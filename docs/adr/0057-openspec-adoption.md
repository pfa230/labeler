# 57. Adopt OpenSpec and freeze the living specification

**Status:** Accepted (supersedes two clauses of [ADR-0001](0001-record-architecture-decisions.md): the
living-specification pairing, and the "major decision" trigger for adding an ADR)

## Context

ADR-0001 paired the ADR log with a single living specification, `docs/SPEC.md`, and required every
major decision to update it in the same change. That worked while the spec was small. It is now a
110 KB monolith covering seventeen subsystems, and the pairing has three costs.

Every change rewrites a section of one large file, so the diff is hard to review and the spec is a
merge bottleneck. The document mixes the current contract with the accumulated history of how it got
there, so a reader cannot tell which parts were settled last week and which have stood for a year.
And nothing links a spec edit to the plan that motivated it: planning artifacts lived in
`docs/superpowers/` (git-ignored), so the reasoning behind a behavior change was discarded once the
change landed.

[OpenSpec](https://github.com/Fission-AI/OpenSpec) addresses the third problem directly. A change gets
its own folder holding a proposal, a design, per-capability delta specs, and a task list. On archive,
the deltas fold into per-capability specs under `openspec/specs/` and the change folder is retained as
history. The planning artifacts are committed rather than discarded.

Migrating the existing 110 KB document into per-capability specs up front would be a large mechanical
edit with no behavioral benefit and a real risk of silently changing a normative rule in transit.

## Decision

- Adopt OpenSpec (CLI 1.9.0) as the workflow for specifying behavior changes: propose, apply, archive.
- **Freeze `docs/SPEC.md`** at commit `bc7b1ce` (2026-08-19). It is no longer edited and receives no
  further changelog entries. It remains the authoritative reference for the behavior it documents.
- Specify new and changed behavior in `openspec/specs/<capability>/spec.md`. `openspec/specs/` starts
  empty and accrues one capability at a time, as changes touch them.
- **Precedence rule.** A frozen `docs/SPEC.md` section stays authoritative until an OpenSpec
  requirement explicitly names and supersedes it, and then only for the section it names.
- **First-touch rule.** The first change to behavior documented only in the frozen spec writes an
  `ADDED` requirement containing the *complete* post-change contract, not the difference, and names
  the `docs/SPEC.md` section it supersedes. `MODIFIED` deltas are only valid against requirements that
  already exist in `openspec/specs/`. This is forced by the tooling: OpenSpec resolves a `MODIFIED`
  delta by locating the existing requirement in the main specs, so a `MODIFIED` against an unmigrated
  section has nothing to resolve against.
- Retain ADR-0001's decision log. Two clauses of its decision are superseded, and nothing else:

  1. *"Pair it with a living specification in `docs/SPEC.md`"* becomes: pair it with an OpenSpec delta
     spec under `openspec/changes/<change>/specs/`, which folds into `openspec/specs/` on archive.
  2. *"Every **major decision** adds or supersedes an ADR"* becomes: **every behavior change** adds or
     supersedes an ADR and adds its index row. This is a widening, not a relaxation: it matches the
     threshold the repository has actually applied since ADR-0001, and it removes the judgement call
     about what counts as "major".
- GitHub issues remain the sole backlog. One OpenSpec change corresponds to exactly one open issue;
  `tasks.md` is execution state for that change, never a place to park future work.
- Retire the superpowers `writing-plans` step for this repository. The OpenSpec change folder is the
  plan, and it is committed.

## Consequences

- Behavior lookup is a two-step read for as long as migration is incomplete: consult `docs/SPEC.md`,
  then check whether an `openspec/specs/` requirement supersedes the relevant section. This is the
  accepted cost of avoiding a big-bang migration, and it shrinks as capabilities migrate.
- The first change to any given subsystem is more expensive than a later one: it must restate that
  subsystem's complete contract as an `ADDED` requirement rather than expressing a small diff.
- Planning artifacts become part of the repository history instead of git-ignored scratch.
- The `openspec` CLI becomes a development dependency. Its generated skill and command files under
  `.claude/`, `.agent/`, `.agents/`, and `.opencode/` are committed but machine-generated: they are
  regenerated by `openspec update` and must not be hand-edited.
- OpenSpec's own archive step is advisory, not enforcing: it offers to archive with unchecked tasks or
  without syncing deltas. `CLAUDE.md` forbids both, and `openspec/config.yaml` repeats them as
  guidance, but the guarantee is process, not tooling.
- CI gains an `openspec` job running `doctor` and `validate`. It checks that specs are well-formed and
  that archived changes are complete; it does not verify that the generated tool files match the
  installed CLI version.
