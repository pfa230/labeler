**Blocking findings.**

1. **Task 2.2 is checked but not performed anywhere: `ink:` on a text item has zero test coverage.** A case-insensitive search for the token `ink` across `src/lib.rs`, `src/templates.rs` and `tests/` returns only the two negative OpenAPI schema assertions (`src/lib.rs:6347`, `6351`) [verified]. No test writes `ink:` on a `text` item and asserts the refusal. This is the change's headline break, the one the proposal and `design.md` justify with "no alias, no deprecation window and no warning path", and the `text-ink` delta's scenario "`ink` on a text item is refused" ("quarantined with an unknown-field error naming `ink` and that item's layout path", "**AND** the server still starts and still serves every other template") is entirely unproven. Adding `#[serde(alias = "ink")]` to `TextRaw.color` (`src/raw.rs:190`) would fail no test. The behaviour is in fact correct, since `PlacementRaw` carries `deny_unknown_fields` (`src/raw.rs:369-371`) and absorbs the flattened remainder, which is what makes the parallel `color`-on-`qr`/`image`/`line`/`container` assertions pass (`src/templates.rs:5977-6035`) [verified]. What is missing is the test, and AGENTS.md is explicit that a checked box is a claim the next reader trusts instead of redoing the work.

2. **Task 6.2 is checked but performed on a text item, not a shape.** The task reads "a template carrying an unreadable colour **on a shape** is quarantined with an error naming the file, the layout path and the field ... and the template write endpoint refuses the same template without writing a file", and `colour-vocabulary`'s scenario names a container declaring `background: chartreuse` with an error naming "the `background` field". The only shape case in the tree, `src/lib.rs:2929-2932` (`background: chartreuse`), sits in the `parse_cases` table of `template_put_paint_refusals_report_correct_reasons` and asserts status and `reason` only, never the layout path, the field, or the absence of a written file. Neither test asserts the field name at all, so the "naming the field" half of the requirement is unchecked on every path, for text as well as for shapes.

**Smaller findings, worth fixing while the above are open.**

3. **`cross_field_paint_equality_between_text_and_container` still cannot fail on the claim it names** (`src/lib.rs:10111-10163`). It paints `color: red` text inside a `background: red` container, then asserts that some pixel is `(255,0,0)` and that `(255,65,54)` appears nowhere. The container fill alone satisfies both, and red glyphs on a red ground are invisible by construction, so the text half is untestable by this fixture. Round-1's finding 2 was answered by the new source-level test `cross_field_paint_equality_emitted_typst` (`src/render/mod.rs:8925`), which does prove it; this pixel test now adds a passing assertion that proves nothing about text. Either give it contrasting colours or drop it.

4. **The shape vocabulary silently widened to accept surrounding whitespace.** `Color::from_str` trims before matching (`src/models.rs:873`), and `DynamicValueVisitor::visit_str` trims again (`src/models.rs:322`), so `background: " red "` (double-quoted, which YAML preserves) now loads. The deleted `parse_color` did not trim: it lowercased the raw string and fell through to `Err(unknown colour ' red ')` [verified against the removed body in the `src/raw.rs` diff]. `colour-vocabulary` calls the set closed and says "a name outside the sixteen" is refused, and no requirement or scenario mentions whitespace. This aligns shapes with what text already did, so it may well be the intended answer, but it is an undeclared behaviour change on `background` and `stroke.color` and belongs in the contract either way.

5. **ADR-0093's Consequences omits the two breaks task 7.1 asked it to record.** Task 7.1 names "the silent value shift for text colours", and `design.md` says that shift "is documented in the proposal, in the `text-ink` removal's migration note, and in ADR-0093".
