**Blocking findings.**

1. **Task 3.6 is checked but not performed for two of its three fields.** No test anywhere renders a `{param}` on `background` or `stroke.color`. Every shape-reference occurrence in the tree is either load-time validation (`src/templates.rs:6134-6241`) or read-back (`src/lib.rs:9887`); the only render-time reference tests use `text.color` (`src/lib.rs:9462`, `9734`, `src/render/mod.rs:8820`). The headline new capability of this change therefore has no end-to-end proof: `colour-vocabulary`'s scenarios "A referenced colour renders on a shape" and "A referenced colour renders on a stroke" (`specs/colour-vocabulary/spec.md`) are untested, and so is the `shape-paint` scenario "A fill may be a parameter reference". Deleting the `resolve_dynamic_value_color` calls at `src/render/mod.rs:2106` and `2115` and hard-coding black would not fail a single test.

2. **The cross-field invariant test cannot fail on the thing it claims to test** (`src/lib.rs:9935-9988`). The fixture puts a solid `background: red` container at `[0,0] size [25,20]` beside a `color: red` text item at `[30,0]`, then asserts only that *some* pixel equals `(255,0,0)` (`src/lib.rs:9970-9977`) and that `(255,65,54)` appears nowhere (`9980-9987`). The container's fill alone satisfies both; the test passes if the glyphs paint black, blue, or anything else that is not Typst's legacy red. Task 6.1's actual requirement — "emits the same paint value for both" — and `colour-vocabulary`'s scenario "the paint emitted for the two items carries the same value" are unproven. It also drops the task's nesting (`text` inside the container) and covers only `red`, not `green`, `gray` and `yellow`.

**Findings that must be fixed before landing.**

3. **An unrelated regression rides along in `src/convert.rs:300`.** The `multiline` migration error was reverted from the wording commit `1e0513c` introduced ("`multiline` on a text item was renamed: use `wrap: true` to enable soft wrapping, or `wrap: false` (the default) to keep hard breaks without soft wrapping") to "multiline is not supported on text; use wrap: true instead". `1e0513c` is an ancestor of HEAD [verified], so this is a revert, not a stale merge base. It is out of scope for #291, and it misdirects the `multiline: false` author, whom the shipped wording sends to `wrap: false`. `text-wrap-flag`'s scenarios only require the error to name the rename, so no test catches it.

4. **A load-time refusal assertion was weakened past the point where it distinguishes the two failures the spec separates** (`src/templates.rs:5947-5952`). It previously required the message to contain `invalid ink '…'` or `expected a named colour`; it now asserts only `err_str.contains("layout[0]")`. `colour-vocabulary`'s scenario "A name outside the sixteen is refused" ends "**and** the failure is colour validation rather than an unrecognised field" — which is exactly what this assertion no longer checks: an implementation that never wired `color` onto `TextRaw` would emit `unknown field \`color\`` at `layout[0]` and pass. (The blanket "names the value" form does not work for the `""` case, whose message is "colour cannot be empty"; asserting the error is not an unknown-field error does.)

5. **Task 7.4 was done as a find-and-replace and left the Purpose wrong** (`openspec/specs/text-ink/spec.md:3-8`). It still claims the capability defines "the colour vocabulary it accepts, its parameter reference form, when a template carrying one is refused, and what it renders to on each output path" — all four of which this change's delta REMOVES from `text-ink` and re-homes in `colour-vocabulary`. After the archive sync the Purpose will describe requirements the file no longer contains. The appended sentence also points a permanent spec at an in-flight change-folder name ("subsumed by the unified `Color` model in `issue-291-one-colour-type`") rather than at the `colour-vocabulary` capability, which is a pointer that goes stale the moment the folder moves into `archive/`.
