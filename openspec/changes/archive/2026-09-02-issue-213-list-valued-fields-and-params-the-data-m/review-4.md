1. **MAJOR — The catalog-index contract is internally impossible.** The delta says a `list` is omitted from every input list regardless of use (`specs/template-inputs/spec.md:31-33`), yet claims an undefaulted list appears in the catalog’s required fields (`:51-55`). The unchanged normative requirement defines catalog fields strictly as required entries from `inputs.all` (`openspec/specs/template-inputs/spec.md:656-663`), matching the implementation (`src/bin/catalog-index.rs:106-111`). An omitted list can therefore never appear, default or not. The artifacts must choose and consistently specify either permanent catalog omission or a deliberate change to catalog derivation.

2. **MAJOR — The claimed existing layout-path diagnostic does not exist, and the design lacks a mechanism for the new guarantee.** The conditional delta says the existing undeclared-`when` refusal names the offending item’s layout path (`specs/conditional-visibility/spec.md:28-36`) and requires the same for a declared list (`:43-45`). The design calls the undeclared behavior unchanged (`design.md:189-195`). In reality, `validate_when_references` receives no path and reports only the parameter name (`src/templates.rs:1403-1419`); its recursive caller also carries no indices (`src/templates.rs:1483-1616`). The plan must distinguish existing behavior from the new list requirement and design explicit path propagation without silently changing unrelated diagnostics.

3. **MAJOR — The plan misses a compile-safe conversion that would publish list defaults as strings instead of arrays.** The contract requires `param_defaults.tags.resolved` to be `["CONSUMABLE"]` (`specs/template-inputs/spec.md:224-229`), and the proposal likewise promises array-valued template-detail data (`proposal.md:60-63`). But `json_to_param_value` currently sends every JSON array through a wildcard that produces `ParamValue::String` (`src/render/mod.rs:364-378`). Adding `ParamValue::List` will not make that wildcard fail compilation, and neither the design nor impact inventory names this conversion (`design.md:331-332`; `proposal.md:172-184`). The design must explicitly preserve arrays through this conversion and require coverage of the serialized template-detail response.

4. **MAJOR — A modified requirement retains token spellings that the same change declares invalid.** The interpolation delta defines only `vars` and `sys` namespace roots (`specs/interpolation-tokens/spec.md:276-285`). Nevertheless, the modified input-list requirement still calls `{datetime}` and `{datetime.<format>}` service-resolved tokens (`specs/template-inputs/spec.md:28-29`) and tests `{datetime.iso_date}` (`:167-171`). The parser rejects `datetime` as an unknown root (`src/interpolation.rs:130-157`). Because a `MODIFIED` requirement must be the complete post-change contract, these clauses and scenarios must use valid `sys.now` spellings.

5. **MINOR — The UI scope is stated contradictorily.** The design lists “no UI change of any kind” as a non-goal (`design.md:46-50`) but later requires edits to `ui/src/api/types.ts` (`:278-299`), matching the proposal’s impact section (`proposal.md:187-193`). The intended distinction appears to be “no UI behavior, component, control, or screen change; API type declarations are updated,” but the plan must say that consistently.

6. **MINOR — The list-default rules contradict themselves over YAML null.** The list requirement refuses every YAML scalar default (`specs/list-params/spec.md:30-33`) but later treats explicit YAML null as an absent default (`:46-47`). Since YAML null is a scalar, the former must say “non-null scalar” or otherwise explicitly exclude null.
