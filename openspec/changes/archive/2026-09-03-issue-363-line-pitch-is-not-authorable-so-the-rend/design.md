# Design: Authorable line pitch (`line_spacing`) on text items

## Context

A `text` item today carries no pitch field (`src/raw.rs:208` lists `value`, placement, `font_size`, `font_weight`, `color`, `wrap`, `alignment`, `overflow`, `when`). The renderer never sets Typst paragraph leading (`src/render/mod.rs` emits `#text(size: …)` blocks joined by `#linebreak()` with no `par(leading:)`), so Typst's default `0.65em` applies, and the fitter mirrors it in `src/render/helpers.rs:1045-1054` (`leading()` plus `metric_block_height`).

On the 1.326 vs 1.3775 discrepancy: the 1.326em figure measures ink tops ("locating the ink bands", issue evidence), while the model predicts baseline pitch. Ink tops are content-dependent: a line's highest ink depends on which glyphs that line carries, so the distance between two different lines' ink tops is not a baseline pitch. The metric model is separately proven: `block_height_matches_typst_layout` (`src/render/mod.rs:6281`) compiles `#linebreak()`-joined lines on an auto-height Typst page and asserts the fitter's prediction matches Typst's laid-out frame height, measured 0.00% off at one to three lines, with the comment that ink extents are the wrong quantity because they include descenders and exclude leading. The derived leading `pitch − cap_height` therefore reuses a stacking the repo already proves against Typst; the new risk is only the emission of a non-default leading, which the extended agreement scenario covers. See `proposal.md` for why this change exists and what it changes.

Two-stage parsing applies: `TextRaw` deserialises under `deny_unknown_fields`, then `TryFrom` in `src/convert.rs` builds the domain `LayoutItem::Text`, with `TemplateDefinition::validate` in `src/templates.rs` covering every construction route (the `font_weight` checks at `convert.rs:383` and `templates.rs:2349` are the precedent for doing both). Read-back serves the domain model directly (`LayoutItem::Text` in `src/models.rs:1070`).

## Goals / Non-Goals

- Goals: one authored pitch number per text item with a spec-pinned default; fitter and emitter agreeing on that pitch with the agreement proven on the render, including below the cap-height ratio; the old font-derived pitch deleted outright; load-time refusal with paths for every bad value including null; the closed unknown-field surface preserved; a worked AUTHORING example.
- Non-Goals: interpolation of the value from params (filed separately); absolute lengths or unit suffixes; inheritance by or from containers; changing the cap-height-to-baseline line box, the ink reservation, or any non-text item; migrating existing templates (pre-1.0 breaking, intended appearance change).

## Decisions

- **New capability `text-line-spacing` plus a `MODIFIED` layout-sizing requirement.** The field's schema, validation, read-back and pitch semantics belong to the new capability, which is the first touch of line-pitch behaviour and therefore carries the complete post-change `text` field list, superseding frozen `docs/SPEC.md` §4.1 in full rather than referring back to it for the unchanged fields. The block-height arithmetic belongs to `layout-sizing`, which already owns `metric_block`, the line budget and the reservation: duplicating those formulas in the new capability would leave two definitions of one block. The `MODIFIED` requirement copies the full "Vertical fitting" block and changes only the pitch/leading definitions, the budget divisor, the supersession note, the re-derived auto-shrink sizes, the narrowed byte-identity scenarios and one added tightening scenario. The "Text is laid out…" requirement needs no edit: it references the metric model generically and its break/shrink/overflow steps are pitch-agnostic. Alternative (everything in the new capability, leaving layout-sizing stale) was rejected as a contradiction between two normative requirements.
- **Bare number meaning baseline-to-baseline multiples, not a Typst leading passthrough.** The issue's survey shows total advance is the dominant meaning across formats while additive leading is the exception; an em-multiple keeps the authored value font-independent, which is the point of the change. A Typst-leading passthrough would bake the face's cap-height ratio into every authored value and reintroduce the font-dependence being removed. Alternative (absolute lengths in template units) was rejected: it is a different model and `1.2` vs `"1.2em"` would be two spellings of one value.
- **Default 1.2, old pitch deleted with no fallback.** Per the issue: `leading()` and the `cap_height + 0.65em` stacking go away; pitch is the authored number or 1.2 everywhere. The emitted Typst leading is derived per item as `pitch(s) − cap_height(s)` measured on the same opsz-instanced face the fitter uses, so the pitch stays constant even though the leading varies slightly with the instance. Fitter and emitter share one function; two copies is how the old model drifted from its own default.
- **Explicit null is refused, as the issue's value contract requires.** The issue says anything that is not a bare number is a parse error, and the issue body is the scope: the earlier null-as-absence draft expanded that scope by analogy and was revised out. Mechanism: presence-tracking deserialisation on the raw field (the `deserialize_present` precedent that already refuses an explicit null for the retired `multiline` key) with the refusal raised in `convert.rs` carrying the key path, plus the range check in both `convert.rs` and `templates.rs validate` so API-submitted templates get the JSON path and every other route is still covered, mirroring `font_weight`. Type errors for strings, booleans, objects and arrays surface from serde with the key path as today.
- **Single-line no-op falls out of the formula.** `metric_block(1, s) = cap_height(s)` contains no pitch term, so no special case exists in spec or code; the scenario pins byte-identity rather than the mechanism. This is also what lets the two retained byte-identity scenarios survive honestly: they are narrowed to single-line items, the only multiline-excluded cases the pitch cannot move, and assert the preserved reservation/placement behaviour there.
- **Acceptance is render-measured on content-controlled values.** Every pitch scenario renders identical repeated lines (`"Hxy\nHxy"`, the probe test's vocabulary: cap-height ink, so corresponding ink bands sit exactly one pitch apart) and measures band distance on the render, never the fitter's arithmetic against itself. The suite spans 0.5 (below the bundled cap-height ratio, exercising negative derived leading), 0.99, the 1.2 default and 1.5, and extends the existing Typst-layout agreement probe to authored leading values so the emission contract is proven, not assumed.
- **The emitted leading is scoped to its text block.** One Typst source carries every item on the label, so a page-level `#set par(leading:)` would leak one item's pitch into the next. The emitter sets the leading inside the item's own block scope.
- **Retained-scenario numbers are re-derived, not carried over.** The auto-shrink scenario's 19.5pt/51.57pt figures were computed under the old pitch by the same static-ratio method, so the delta recomputes them the same way: 21.0pt chosen, 59.04pt demanded at 24.5pt. The stale pre-reservation counterfactual is dropped rather than re-proven: it compared against an era, not a requirement, and adds nothing this change needs.

## Risks / Trade-offs

- **Tight values need zero or negative Typst leading.** `line_spacing` below the face's cap-height ratio (~0.73 bundled) makes the derived `pitch − cap_height` zero or negative. Typst `par.leading` is a length and lengths admit negatives, but this is proven by the new 0.5-pitch render scenario, not by reading: any value in the accepted range must render at its pitch, so a failure there fails acceptance rather than slipping through.
- **Broad golden-test fallout.** The default moves 1.3775em to 1.2em on the bundled font, so every existing render expectation keyed to multi-line fitting (fitted sizes, line counts, ellipsis markers, catalog fixtures) is suspect until re-run. [Risk] → Mitigation: re-baseline by running the suite, and the diff reviewer checks each updated expectation is explained by the pitch change and nothing else.
- **`cap_height` still varies by face.** The first-line cap box remains font-derived, so swapping `LABELER_FONTS_DIR` still moves single-line placement slightly; only the pitch, the quantity that compounded per line, becomes font-independent. This is inherent to the retained cap-box model, not a leak in this change.

## Migration Plan

Pre-1.0 breaking change, no stored data involved (`store.rs:154-168` does not apply). No migration, no shim. Rollout is the single commit; rollback is revert. `docs/AUTHORING.md` is updated in the same commit, so no template author reads a stale example.

## Open Questions

None. Every value in the contract (name, type, default, validation including null, scope, static-only) is pinned by the issue; the capability split follows the existing spec organisation.
