    50	## Decisions
    51	
    52	**A connection carries two addresses with distinct jobs, and the ADR says so.** `base_url` is the
    53	address Labeler dials; `public_url` is the address Labeler prints. This change adds
    54	**ADR-0061, "A connection's public URL is the link base, its base URL is the fetch base"**, plus its
    55	row in `docs/adr/README.md`. 0059 and 0060 are taken by the changes that merged while this one was
    56	being planned, so 0061 is the next free number.
    57	
    58	It supersedes the **Connections store** decision of
    59	[ADR-0018](../../../docs/adr/0018-api-integration-spine.md), which records the connection row as
    60	`(connector, name, base_url, credential, enabled)`
    61	(`docs/adr/0018-api-integration-spine.md:39-42`) and would otherwise stand as an accepted record
    62	contradicting the field this change makes reachable. Only that decision is superseded: ADR-0018's
    63	browse-cursor, connector-schema, and Homebox-endpoint decisions stand, so ADR-0018 keeps the status
    64	`Accepted` with its row noting the partial supersession. ADR-0060 amended the same record from the
    65	transform side without superseding ADR-0018; both amendments stand and neither contradicts the other.
    66	The `public_url` server work itself landed in commits `d18ebad`, `2eafccf`, `78504a3` on 2026-08-17
    67	with no ADR at all, which is the gap this closes.
    68	
    69	*Alternative considered:* one URL plus a rewrite rule (store only `base_url` and a host substitution
    70	applied at link time). Rejected: it encodes the same information less directly, and an operator
    71	reasoning about "what does the QR code point at?" would have to apply the rule mentally.
    72	
    73	**Clearing is expressed as `null`, and the form always sends the key.** The API distinguishes
    74	key-absent (keep) from `null`/blank (clear), which exists for API clients doing partial updates. The
    75	form is not a partial update: it renders every field, so it always sends `public_url`, as `null` when
    76	the input is blank. That makes "empty the box and save" clear the stored value, which is the only
    77	behavior an operator would predict from a text input, and it is how the form already treats
    78	`transforms` (`ConnectionsSection.tsx:57`).
    79	
    80	*Alternative considered:* omit the key when blank. Rejected: it makes the field write-once from the
    81	UI, with no way to undo a public URL short of a hand-written request.
    82	
    83	**Field-typed URL validation.** `validate_and_normalize_url` gains a small `UrlField` enum
    84	(`Base`/`Public`) in place of its `&str` field name, with the wire name and the `Reason` hanging off
    85	it. One value decides both the message text and the discriminator, so the two cannot drift, and the
    86	call sites stop passing a bare string that controls neither. `Reason::PublicUrlInvalid =>
    87	"public_url_invalid"` joins the `reasons!` macro list in `src/reason.rs`; adding a slug is additive
    88	and breaks no client, since only renames are breaking (`src/reason.rs:3`). No test scaffolding is
    89	needed for the new slug: `src/errors.rs:577-600` already counts a slug as documented when an OpenSpec
    90	spec names it in backticks, and `specs/connections/spec.md` names this one.
    91	
    92	*Alternative considered:* keep the `&str` parameter and add a `Reason` parameter beside it. Rejected:
    93	two parameters that must agree is exactly the drift the enum removes.
    94	
    95	*Alternative considered:* leave the discriminator as `base_url_invalid`. Rejected as recorded in this
    96	change: a machine-readable reason that names the wrong field is worse than no distinction at all, and
    97	the UI's own error text comes from `message`, so nothing else compensates.
    98	
    99	**Userinfo is rejected in both URL fields.** A connection URL is printed into QR codes and rendered as
   100	a browser link, so `https://user:pass@homebox.example.com` would put credentials on a physical label.
   101	Rejecting it on `public_url` alone would leave two fields with two validation rules and one spec
   102	carrying the exception, so the rule applies to both. It bites only at write time: a stored `base_url`
   103	with userinfo keeps working until someone saves that connection.
   104	
   105	*Alternative considered:* accept userinfo and document the hazard. Rejected as recorded in this
   106	change; validation that already checks scheme, host, query, and fragment has no reason to wave through
   107	the one component that leaks a secret.
   108	
   109	**The UI validates the public URL exactly as it validates the base URL, and only when non-blank.**
   110	`ConnectionForm` already parses `base_url` with `new URL()` and checks the protocol before sending
   111	(`ConnectionsSection.tsx:47-49`); the public URL reuses that shape so both fields fail the same way,
   112	in the form, without a round trip. Blank skips validation entirely, because blank is a legal value
   113	meaning "none".
   114	
   115	**The table gets a Public URL column.** The form is per-connection; the column answers "which of these
   116	print external links?" at a glance, which is the question an operator debugging a scanned QR code
   117	actually has. An unset value renders `-`, matching the table's habit of rendering a short token
   118	(`set`/`none`, `yes`/`no`) rather than an empty cell.
   119	
   120	**The `connections` capability names `transforms` but owns nothing about it.** Writing the record whole
   121	is what the first-touch rule asks for, and leaving `transforms` out would make the record wrong the day
   122	it is archived. Restating its rules would duplicate `connector-field-transforms` and invite the two to
   123	drift, so the record requirement names the field and points at that capability for every rule.
   124	
   125	*Alternative considered:* a `MODIFIED` delta against `connector-field-transforms`. Rejected: that
   126	capability's requirement is about transforms, not about the connection record or its URLs; widening it
   127	to carry `public_url` would put two unrelated contracts in one requirement.
   128	
   129	**`connector` on `PUT` is documented as inert, not made strict.** The update handler never reads
   130	`body.connector`, so a payload naming a different or unknown connector is accepted and changes nothing,
   131	while `POST` rejects an unknown one. The spec records that as the contract rather than tightening it:
   132	rejecting a mismatched connector on update is a behavior change outside #169's scope, so it is filed as
   133	[#197](https://github.com/pfa230/labeler/issues/197) and left out of this change.
   134	
   135	**Server code is verified against the spec, not rewritten.** Apart from the reason and userinfo
   136	changes, the tasks read the existing store, API, and connector paths against each requirement and add a
   137	test only where one is missing. The spec is being written after the implementation here, so the
   138	verification step is what makes the two match rather than merely appear to.

   141	
   142	- **The spec is written from the code it describes, so a bug in the code becomes a bug in the spec.**
   143	  → The requirements were drafted from the API contract and the issue's intent, then checked against

   152	- **Two capabilities now describe the same connection record.** → `connections` owns the record and

     1	## Purpose
     2	
     3	Defines the connection record that binds Labeler to an upstream inventory system, its CRUD contract,
     4	and the two addresses a connection carries: the base URL Labeler fetches from and the optional public
     5	URL that Labeler puts into the links and QR codes it generates for people.
     6	
     7	## ADDED Requirements
     8	
     9	### Requirement: Connection record
    10	
    11	A connection SHALL be `{ id, connector, name, base_url, public_url, transforms, credential, enabled }`,
    12	persisted by the server. `public_url` SHALL be optional and default to absent. The credential SHALL
    13	never be returned by any endpoint; responses SHALL expose it only as the boolean `has_credential`;
    14	`transforms` SHALL be returned in full.
    15	
    16	This requirement supersedes the connection record shape in the frozen `docs/SPEC.md` §12
    17	("Integrations (connectors)"). Every other part of §12 remains authoritative. `transforms` is named
    18	here only so the record is stated whole: every rule about what a transform is, when it is accepted,
    19	and what it derives belongs to `connector-field-transforms`, which this requirement neither restates
    20	nor alters.
    21	
    22	`GET /api/connections` SHALL list every connection ordered by `name`; `GET /api/connections/{id}`
    23	SHALL return one, or `404` when the id is unknown.

    27	- **WHEN** a client reads a connection through `GET /api/connections` or `GET /api/connections/{id}`

    29	  `enabled`, and `has_credential`
