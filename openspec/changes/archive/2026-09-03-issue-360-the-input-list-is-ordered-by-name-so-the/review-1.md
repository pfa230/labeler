1. **MAJOR — The new requirement claims ownership of a contract already migrated to OpenSpec.** `specs/template-inputs/spec.md:5-26` adds a partial requirement claiming to supersede frozen §3.0. However, `openspec/specs/datetime-params/spec.md:236-314` already supersedes §3.0 and holds the complete parameter-type contract, while `openspec/specs/interpolation-tokens/spec.md:385-403` owns parameter naming. `openspec/config.yaml:65-73` requires subsequent changes to use `MODIFIED`. The plan must modify the existing owning requirement—or explicitly repartition its ownership through a modification—instead of adding a competing, incomplete supersession. The same issue affects the §3 field-table claim at `specs/template-inputs/spec.md:7`, since that table already lives in `template-groups` and is modified separately here.

2. **MAJOR — An existing wire-contract scenario remains contradictory.** The published requirement at `openspec/specs/template-inputs/spec.md:1555-1656` says `GET /api/templates` summaries carry `params` “exactly as before.” The proposal changes that endpoint from an object to an array (`proposal.md:26`), and the issue explicitly asks for deltas to the requirements carrying summary/detail params (`.agent-runs/issue-360.md:72-75`), but the change does not modify this requirement. After archive, the main spec would contain both the new array rule and the unchanged “exactly as before” assertion. A complete `MODIFIED` delta for that existing requirement is required.

3. **MAJOR — The declared error-precedence change has no normative delta.** The proposal says parameter-processing errors will change from name order to declaration order (`proposal.md:35`), and the design makes that an intentional rule across validation, conversion, and resolution (`design.md:44`, `design.md:65`). The only ordering rule in the delta governs input-list entries (`specs/template-inputs/spec.md:182`); nothing specifies which error wins when multiple declarations are invalid. Because AGENTS.md treats the error contract as behavior requiring a delta (`AGENTS.md:61-72`), the plan currently permits an implementation that preserves alphabetical error precedence while still satisfying every proposed requirement.

4. **MAJOR — Empty-parameter responses are left with two permitted shapes.** `specs/template-inputs/spec.md:24` allows an omitted `params:` declaration to be published either as `[]` or with the field omitted “as the schema permits.” Today both summary and detail always serialize the field (`src/models.rs:62`, `src/models.rs:101`), while the proposal promises that `params` “becomes an array” on both response shapes (`proposal.md:26`). Permitting omission introduces an additional, unspecified wire break and contradicts the stated “one field, one shape” design. The contract must choose one result; preserving current field presence means requiring an empty array.

VERDICT: REVISE
