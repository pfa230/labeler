## Blocking

**1. Switching Import to a sheet template steals focus from the template picker.** `LabelGrid.tsx:642-653` focuses the first editable control whenever `!onSelectRow && rows.length > 0` and `initialFocusDone` is unset, on deps `[onSelectRow, disabled, rows]`. Until this diff both pages always passed `onSelectRow`, so that branch only ever ran in the template-inputs fixture. Now `Import.tsx:490` flips `onSelectRow` to `undefined` when the operator picks a sheet template while a grid is loaded; the grid is not remounted (CsvEditor is unkeyed), so the effect fires mid-session. [verified] I ran a scratch test (written to and deleted from `ui/src/pages/`, tree unchanged): after loading a 2-row CSV under the single template, focusing the picker and changing it to `sheet-tpl`, `document.activeElement` is the row-1 `edit sku` text input, not the select. A keyboard user arrowing through templates loses the picker at the first sheet template. Neither the delta nor `design.md` names focus movement for a sheet grid; the proposal only says the "freshly mounted" fixture becomes the sheet grid's ordinary state, and this is not a mount. Connect is keyed on `detail.id`, so it only hits the mount case, which the template-inputs scenario does prescribe. Fix belongs in `LabelGrid`: consume `initialFocusDone` on the first render that has rows regardless of whether the column is present, so a later prop change cannot trigger it; add an Import test that a loaded grid plus a picker change to a sheet template leaves focus on the picker.

**2. The "no batch request" assertions in 5.3, 5.5 and 5.6 cannot fail.** `Connect.test.tsx:2931,2991,3045` and `Import.test.tsx:1308,1368,1420` assert zero requests immediately after `waitFor` sees the message (or, in 5.6, "rendering preview…", which is present from mount). `waitFor` checks its callback synchronously on entry and the message is in the DOM from the same `act`-wrapped `fireEvent`, so the assertion runs within a few ms of the edit, while an implementation that ignored `blocked` or `rowsPending` would send its request 300 ms later (`sheetPreview.ts:37`). In 5.3 the repair follows inside the same window, so even the wrong request would be cancelled by the key change. These three task boxes claim what the tests do not earn. The hook-level `enabled: false` case does advance 500 ms (`sheetPreview.test.ts:112-120`), but tasks 5.3, 5.5 and 5.6 are page-level claims. Fix: advance past the debounce before each zero assertion, as 5.8 already does at `Connect.test.tsx:3141` / `Import.test.tsx:1518`.
