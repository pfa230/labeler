   169	## Architecture
   170	
   171	Request path `api.rs → render/`; template path `templates.rs → parse.rs → raw.rs → convert.rs`.
   172	
   173	- **Two-stage parsing.** YAML deserializes into `raw.rs` structs (all `deny_unknown_fields`), then
   174	  converts to the domain model via `TryFrom` in `convert.rs`, with `serde_path_to_error` attaching a
   175	  JSON path to every error. This lets the wire format differ from the validated model. *Adding a
   176	  layout field means editing three files together: `raw.rs`, `models.rs`, `convert.rs`.*
   177	- **Template registry.** Loaded and `validate()`d at startup (`main.rs`). A template that fails to
   178	  parse or validate is **quarantined** and the server still starts (#175); so is a file whose id is
   179	  already taken, with the lexicographically first filename keeping the id (#181, ADR-0058). No
   180	  template content is fatal. Nothing is seeded into a fresh config dir. Templates are immutable,
   181	  shared via `Arc`.
   182	- **Layout model** (`models.rs`). `layout` is a tree of `LayoutItem`s: `Text`, `Qr`, `Image`, `Line`,
   183	  `Container`. `Container` nests `items` recursively and may carry `frame` and `padding`. Any item may
   184	  carry `when:`, the universal conditional-visibility predicate over `params` (ADR-0056, #162).
   185	  Write new templates with `params` + `when`, but note the legacy top-level `options:` map and
   186	  `container.option` still **parse**: they desugar into an enum `params` entry and into `when`
   187	  (`convert.rs:284`, `convert.rs:107`). Do not treat a template using them as invalid.
   188	- **Coordinates.** Bottom-left origin, y-up, in the template `unit` (`mm` or `in`). Typst is top-left,
   189	  so the renderer flips with `frame_height_units - top`. A `Container` re-bases children into its
   190	  padded inner box via a fresh `RenderContext`. *Watch this when touching placement math.*
   191	- **Sizing.** `size` is a number or `auto`. `auto` resolves to `max_w`/`max_h` if given, else (for
   192	  containers and lines) the parent frame. *This logic is duplicated between compile-time validation
   193	  (`templates.rs`) and render-time resolution (`render/mod.rs`); keep the two in sync.*
   194	- **Rendering** (`render/mod.rs`). Walks the layout emitting Typst markup; PNG via `typst-render`,
   195	  sheets as one clipped box per slot via `typst-pdf`. `render/helpers.rs` holds string escaping,
   196	  length formatting, QR-SVG generation (`qrcode`), and `ttf-parser`-based text fitting for
   197	  `font_size: {min, max}` (auto-shrink plus ellipsis truncation).
   198	- **Errors.** `TemplateError` (parse/validation, carries a path) quarantines rather than aborting
   199	  startup. `AppError` is the HTTP error, serializing to `{ "error": { code, message, details } }`. Add
   200	  new kinds as `AppError` constructors so `code` strings stay stable.
   201	- **OpenAPI.** Every model exposed in the API must be registered in `src/openapi.rs`.

     2	
     3	See `proposal.md` for motivation and `specs/template-groups/spec.md` for the contract. What shapes
     4	the approach here:
     5	
     6	- Templates are files. The registry loads `{config}/templates/*.yaml` one level deep
     7	  (`src/templates.rs:95`), keys on the `id` inside each file, and remembers which file each id came
     8	  from (`src/templates.rs:190`). `POST /api/templates` writes `{id}.yaml`; every other write resolves
     9	  the path through the registry rather than guessing at a filename (`src/api.rs:332`).
    10	- Parsing is two-stage and rejects unknown fields: YAML → `TemplateDefinitionRaw` (`src/raw.rs:104`)
    11	  → `TemplateDefinition` via `TryFrom` (`src/convert.rs:265`), then `validate()`
    12	  (`src/templates.rs:306`) returns a human message. A file that fails either is quarantined, not
    13	  fatal (`openspec/specs/template-registry/spec.md`).
    14	- ADR-0006 forbids a GUI from rewriting a hand-authored template, because a YAML parse-and-re-emit
    15	  round trip destroys comments and normalizes key order. That ADR is the reason the editor is a raw
    16	  source textarea today (`ui/src/pages/TemplateDetail.tsx`).
    17	- The Labels page loads the full template list once and derives Favorites and Recents from it
    18	  (`ui/src/pages/Templates.tsx:107`), so it already holds every summary in memory.
    19	
    20	## Goals / Non-Goals
    21	
    22	**Goals:**
    23	
    24	- Group assignment is a one-click action from the Labels page, on one card or on many, and never
    25	  requires typing YAML.
    26	- A move changes exactly one line of the file and leaves comments, key order, and formatting intact.
    27	- The group survives export, backup, catalog install, and copying a file to another machine.
    28	- Nothing about grouping can take the service down or make a template unrenderable.
    29	
    30	**Non-Goals:**
    31	
    32	- Hierarchy. `Shipping/Pallets` is a name, not a path (decision 2).
    33	- Group entities. There is no create-group or delete-group operation and no place a group is stored
    34	  apart from the templates naming it, so an empty group cannot exist.
    35	- Renaming a group across every template that uses it, and drag-and-drop onto a filter chip. Neither
    36	  is part of #164, and neither is queued: each gets its own issue if and when it is wanted.
    37	- Directory reorganization. `{config}/templates/` stays one flat level.
    38	
    39	## Decisions
    40	
    41	### 1. The group is a YAML field on the template, not a directory and not a store row
    42	
    43	Alternatives were directory mapping (`templates/<group>/x.yaml`) and a row in the SQLite store
    44	beside favorites.
    45	
    46	Directory mapping loses on four counts, all in code that exists today. The loader walks one level
    47	(`src/templates.rs:95`) and every downstream identity is a basename, including `BrokenTemplateSummary.filename`
    48	(`src/models.rs:36`) and the duplicate-id tie-break just frozen in `template-registry` ("the one whose
    49	filename sorts first in byte order"); recursion turns all of those into relative paths and reopens a
    50	requirement written days ago. It puts a caller-supplied string on the write path, where
    51	`template_file_path` currently derives the filename from an id restricted to `[A-Za-z0-9_-]`
    52	(`src/api.rs:310`), so a group segment would need its own traversal, separator, and case-collision
    53	guards on an endpoint that writes files. It turns a regroup into mkdir plus cross-directory rename
    54	plus pruning the emptied directory, with a half-failed state the current single atomic rename does
    55	not have. And it puts the group outside the artifact, so a catalog install (`ui/src/pages/Catalog.tsx:127`
    56	POSTs the YAML body) arrives ungrouped.
    57	
    58	Store metadata fails the portability test the same way, and additionally splits template truth across
    59	a file and a database, which is what ADR-0006 exists to prevent.
    60	
    61	The YAML field costs one field in each of the three parse-path files and nothing else. Its one real
    62	loss: reorganizing `/config/templates` by hand with `mv` does not group anything, because the
    63	directory carries no meaning. Accepted knowingly.
    64	
    65	Recorded as **ADR-0062, "A template's group is a YAML field, not its directory"**.
    66	
    67	### 2. One flat level
    68	
    69	`group` is a single name. The service does not split on `/` or any other character, so
    70	`Electronics / Cables` is one group whose name happens to contain a slash.
    71	
    72	Hierarchy was rejected for this change, not forever: it costs a tree control with expansion state in
    73	the Labels view, a decision about whether selecting a parent includes its children, per-segment
    74	validation, and a depth cap, for a set that is currently a few dozen templates. Widening later is a
    75	pure loosening of `validate_group_name`, and no existing file or response has to change, so the
    76	cheap option here does not become the wrong one later. Same ADR-0062.
    77	
    78	### 3. Validation lives in one function, shared by the parse path and the move endpoint
    79	
    80	`validate_group_name(&str) -> Result<String, String>` returns the whitespace-stripped name or a
    81	message naming `group`. It is called from `TemplateDefinition::validate()` (so a bad group quarantines
    82	the file like any other validation failure) and from the move handler before it patches anything (so a
    83	bad name is a `422` with nothing written). One definition, so the file path and the API path cannot
    84	drift.
    85	
    86	The domain model stores the stripped value: `TemplateDefinition.group: Option<String>`, `raw.rs` gains
    87	`group: Option<String>` with `#[serde(default)]`, and `convert.rs` strips on the way through. A
    88	non-string value fails at deserialization with `serde_path_to_error` naming `group`, which is why the
    89	spec says "parse or validation message" rather than naming one.
    90	
    91	Bounds: non-empty after stripping, at most 64 characters, no control characters. 64 is a display
    92	bound, not a storage one: these names sit in a filter row and on cards.
    93	
    94	Case is significant, so `Warehouse` and `warehouse` are two groups. Case-folding would be wrong for
    95	`3M` and `pH`, and cross-file collision detection would need a registry-wide rule for something that
    96	is only a naming preference. The mitigation is in the UI: the move dialog offers the names already in
    97	use, so the normal path picks an existing name instead of retyping it.
    98	
    99	### 4. Move is `PUT /api/templates/{id}/group`, a targeted single-line file patch
   100	
   101	The endpoint replaces one subresource and is idempotent, which is `PUT`, not `PATCH`.
   102	
   103	The patch is textual, never a parse-and-re-emit, which is what keeps it inside ADR-0006's intent
   104	rather than against it. Under `state.write_lock`, with the path resolved through the registry
   105	(`existing_template_file`), the handler:
   106	
   107	1. reads the stored file;
   108	2. refuses a file holding more than one YAML document (`422`), since "the top-level `group`" is
   109	   ambiguous there;
   110	3. finds a top-level `group:` line: a line whose first character is at column 0, that is not a
   111	   comment, and whose key is exactly `group`. Column 0 is what makes a nested `group:` key
   112	   (inside `params`, or a layout item) unreachable, since nested keys are indented;
   113	4. cross-checks that scan against the parsed template. The parser accepts spellings the scan does not
   114	   recognize, `"group": Shipping` among them, so when the parsed template has a group and the scan
   115	   found no line to replace, or found more than one, the handler refuses with `422` instead of
   116	   inserting. Without this check step 7 would append a second top-level `group` key;
   117	5. if the matched line's value is not a scalar it can replace in place (a block scalar `|`/`>`, a
   118	   flow collection, an anchor or alias, or an empty value introducing a nested block), refuses with
   119	   `422` rather than guessing. Plain and quoted scalars are both replaceable, which matters because
   120	   `group: "Shipping"` is a valid and expected spelling;
   121	6. builds the new line as `group: ` plus the name emitted through the YAML serializer, so a name
   122	   needing quotes gets them, and re-attaches any trailing comment the old line carried;
   123	7. for a clear, deletes the whole line and its terminator; for an insert, places the new line
   124	   immediately after the top-level `name:` line, falling back to after `id:`, then to the top of the
   125	   document body after any leading comments and `---` marker;
   126	8. parses and validates the patched text, and asserts the group reads back as requested. Only then
   127	   does it write, through the same atomic temp-then-rename as every other template write, and reload
   128	   the registry.
   129	
   130	Step 8 is the safety net that makes the textual patch acceptable: a patch that would produce a file
   131	the service cannot load never reaches the disk. Step 4 is the one that keeps a *loadable* file from
   132	being wrong: a duplicated key can round-trip through a parser that takes the last value, so the
   133	scan-versus-parse disagreement has to be caught before the write, not after it. Line endings are preserved by splitting on line
   134	terminators and keeping each line's own ending, so a CRLF file stays CRLF.
   135	
   136	Recorded as **ADR-0063, "The service may rewrite one key of a hand-authored template"**, which
   137	qualifies ADR-0006: a targeted single-key patch that preserves every other byte is not the lossy
   138	round trip that ADR forbids, and the guarantee is enforced by tests that assert byte equality outside
   139	the patched line.
   140	
   141	New reasons in `src/reason.rs`: `template_group_invalid` (`422`, a name that fails validation) and
   142	`template_group_unpatchable` (`422`, a file the patcher will not touch). Existing reasons cover the
   143	rest: `template_id_invalid`, `template_write_failed`, `template_registry_io`.
   144	
   145	### 5. The server filters, the UI does not have to
   146	
   147	`GET /api/templates?group=` exists for API clients, and its three states (absent, a name, empty) are
   148	distinguishable in axum as `Option<String>` from `Query`, so "all" and "ungrouped" do not collide.
   149	
   150	The Labels page keeps fetching the unfiltered list and filters in the browser, because it needs the
   151	full set anyway to resolve Favorites and Recents (`ui/src/pages/Templates.tsx:107`) and to build the
   152	filter row itself. Refetching per filter selection would add a round trip and make the group list
   153	depend on the current filter. The endpoint parameter and the UI's client-side filter are specified to
   154	mean the same thing, and the API tests are what hold them together.
   155	
   156	### 6. UI shape
   157	
   158	- A filter row above the grid: `All`, each group in use in ascending order, `Ungrouped` only while
   159	  something is ungrouped. Selection is component state, composed with the existing search box by
   160	  `useMemo`, so both narrow at once. A selection other than `All` also hides the Favorites and
   161	  Recents rows, reusing the `searching` condition already in `ui/src/pages/Templates.tsx:137`: those
   162	  rows are drawn from the whole set, and leaving them on screen under a group filter would show
   163	  cards from the groups the user just filtered out.
   164	- Each card shows its group next to the format badge, and gains a **Move to…** item.
   165	- The move dialog is a text input over a `<datalist>` of the groups in use, plus a "Make ungrouped"
   166	  action. Typing an unused name and confirming creates that group by moving a template into it.
   167	- Multi-select: a checkbox per card and a selection bar reading "N selected · Move to…". A bulk move
   168	  issues one request per template with `Promise.allSettled`, then reports successes and failures
   169	  per template, so a partial failure is visible rather than silent.
   170	- One `useMoveTemplateGroup` mutation invalidating the `templates` query, so the grid and filter row
   171	  both refresh from the server's answer rather than from optimistic local state.
   172	
   173	## Risks / Trade-offs
   174	
   175	- **The patcher corrupts a hand-authored file.** → It never writes text the service cannot parse and
   176	  validate (step 7), the write stays atomic, and the tests assert byte equality outside the patched
   177	  line across the whole `catalog/` tree, which is the real corpus of comment-carrying templates.
   178	- **A move silently overwrites a source edit open in another tab.** The editor PUTs the whole file
   179	  with no version check, so a stale draft saved after a move reverts the group. This hazard exists
   180	  today between two editors; grouping widens it to a second writer. Documented here, and optimistic
   181	  concurrency on template writes is a separate issue rather than a rider on this one.
   182	- **Rollback quarantines grouped templates.** `deny_unknown_fields` means a binary from before this
   183	  change rejects a file carrying `group:`. Per `template-registry` those files are quarantined and
   184	  reported as broken, not fatal, so an older binary starts and serves everything else. Recovery is to
   185	  roll forward, or to delete the `group:` lines. Stated in ADR-0062's consequences.
   186	- **Group names drift by case and spelling.** Only the dialog's list of existing names pushes against
   187	  it. Deliberate: enforcement would mean a registry-wide uniqueness rule for a naming preference.
   188	- **Bulk move is N requests.** At a few dozen templates that is fine; a bulk endpoint is not worth its
   189	  contract until the count justifies it.
   190	
   191	## Migration Plan
   192	
   193	No data migration. Every existing template, request, and response stays valid, and `group` is omitted
   194	from responses when unset, so no consumer sees a shape change. Deployment is the normal image roll
   195	(ADR-0016); rollback is the previous image, with the caveat above.

     2	
     3	## Purpose
     4	Defines how the templates directory is turned into the served template registry: which files are read, what happens to a file whose content is unusable, how two files claiming one id resolve, and how the refused files are reported to the operator. The registry is rebuilt from disk by this same contract at startup and on every reload.
     5	
     6	## Requirements
     7	
     8	### Requirement: Startup survives every template content fault
     9	
    10	The service SHALL start whenever the templates directory is readable, regardless of the content of the files in it. A file that fails to parse, fails validation, or claims an id another file already holds SHALL be excluded from the served set and reported as broken, and SHALL NOT abort startup.
    11	
    12	The service SHALL abort startup only when the templates directory itself cannot be read or enumerated, or an individual file cannot be read.
    13	
    14	This requirement supersedes the `docs/SPEC.md` §3 sentence "Parsing rejects unknown fields (`deny_unknown_fields`). An invalid template aborts server startup." for its second sentence only; unknown-field rejection is unchanged.
    15	
    16	#### Scenario: A malformed file does not stop the service
    17	
    18	- **WHEN** the templates directory holds one valid template and one file that is not valid template YAML
    19	- **THEN** the service starts
    20	- **AND** the valid template is served
    21	- **AND** the malformed file is reported as broken
    22	
    23	#### Scenario: An unreadable templates directory is fatal
    24	
    25	- **WHEN** the templates directory cannot be read
    26	- **THEN** the service exits with a fatal error naming the directory
    27	
    28	### Requirement: Templates load in a deterministic order
    29	
    30	The registry SHALL load the files of the templates directory whose extension is `yaml` or `yml`, compared case-insensitively, in ascending byte order of filename, independent of the order the filesystem enumerates them. Files with any other extension SHALL be ignored.
    31	
    32	Two loads of the same directory contents SHALL therefore produce the same served set, the same id-to-file mapping, and the same broken list, on any machine.
    33	
    34	#### Scenario: Load result does not depend on filesystem order
    35	
    36	- **WHEN** the same set of template files is loaded on two machines whose directory enumeration order differs
    37	- **THEN** both loads serve the same templates from the same files
    38	- **AND** both report the same broken files
    39	
    40	### Requirement: A duplicate template id refuses the colliding file
    41	
    42	When two or more files in the templates directory declare the same template `id`, the registry SHALL serve the one whose filename sorts first in byte order (so `Z.yaml` sorts before `a.yaml` on a case-sensitive filesystem) and SHALL refuse each later file for that id.
    43	
    44	A refused file SHALL:
    45	
    46	- be excluded from the served set, leaving the winning file's template served and unchanged;
    47	- appear in the broken list, identified by its own filename;
    48	- carry an error message naming the duplicated id, and the filename of the file it collides with.
    49	
    50	Refusing a colliding file SHALL NOT eject, alter, or invalidate the template already accepted for that id, and SHALL NOT affect any other template in the directory.
    51	
    52	A duplicate id SHALL NOT produce an HTTP error response. The `template_duplicate_id` reason of `docs/SPEC.md` §10.1 therefore no longer reaches the wire: it names the cause carried in a `broken` entry's message, and no request can provoke a `TemplateInvalid` response carrying it.
    53	
    54	This requirement supersedes the `docs/SPEC.md` §3 top-level field table entry for `id` ("Required, non-empty, unique across the directory") to the extent of what a collision does: the id remains required and non-empty, and uniqueness is now enforced by refusing the colliding file rather than by refusing to run.     55

    85	### 2.0 Template management
    86	
    87	Templates are hand-authored YAML in the templates dir and may also be managed over the API. The
    88	registry is held in an `ArcSwap` for lock-free reads; `reload` and every mutation rebuild it from disk
    89	and swap atomically. A reload that fails (an invalid file on disk) returns `422` and keeps the
    90	previously-loaded set, so a bad file never takes the service down.
    91	
    92	- `POST /templates/reload` re-scans the dir and returns `{ "count": N }`.
    93	- `POST /templates` creates from a raw YAML body; the `id` comes from the body; `409 Conflict` if it
    94	  already exists.
    95	- `PUT /templates/{id}` replaces from a raw YAML body; the body `id` must equal the path `{id}` (else
    96	  `400`); `404` if it does not exist. A `422` has two sources and they differ in effect: the submitted
    97	  body failing `parse_and_validate`, which is rejected before anything is written, or the directory
    98	  reload that *follows* a successful write finding some other template invalid — in which case the
    99	  file has already been replaced while the registry keeps the previous set, and retrying the save once
   100	  the directory is valid converges. Callers must not read a `422` as "nothing was saved".
   101	- `DELETE /templates/{id}` removes the template's backing file and returns `204`; `400` on an invalid
   102	  id, `404` when the registry holds no such id, `422` when the file was removed but reloading the
   103	  directory then found some *other* template invalid (the previous set stays live, so the deleted id
   104	  lingers in memory until a later reload succeeds; retrying the delete once the directory is fixed
   105	  converges). The delete is permanent: nothing re-seeds templates
   106	  (the binary has shipped none since #137), so a deleted template does not return on restart. It also
   107	  drops every user's favorite for that id, so a later template reusing the id does not inherit them.
   108	  Recents are left alone: they derive from the print-job log, and deleting a template must not erase
   109	  the record that labels were printed from it (ADR-0048).
   110	- `GET /templates/{id}/source` returns the raw stored YAML (`text/yaml`) for the read-only source view;
   111	  `400` on an invalid id, `404` if the file is missing.
   112	- `GET /templates/{id}/thumbnail` renders a representative PNG for the template using placeholder data
   113	  (each field filled with its field name, each QR code encoded with its field name). For `single`
   114	  templates it renders the one label. For `sheet` templates it renders a single label slot (not a full
   115	  sheet) so the preview is label-sized regardless of format. Variables (`{vars.X}`) are resolved from
   116	  the store; undefined variable references cause a `422`. The default option selection (first allowed
   117	  value per option key) is used automatically. The response carries `ETag` (a quoted SHA-256 of the
   118	  rendered PNG bytes, so it moves with the template, the renderer, the interpolated variables and the
   119	  datetime formats alike; #129) and `Cache-Control: no-cache`; callers that send `If-None-Match` with a matching ETag
   120	  receive `304 Not Modified`. Error codes: `404 TemplateNotFound` for unknown ids, `422` for
   121	  render/interpolation failures.

   134	### 2.1 `POST /render/label`
   135	
   136	```json
   137	{
   138	  "template": "brother_18mm_qr",
   139	  "data": { "message": "Hello", "code": "QR-123" }
   140	}
   141	```
   142	
   143	- Renders a single label as a preview or one-off; for multi-label work and printing, use `POST /batch`.
   144	- `template` must reference a template whose `format.type` is `single`; otherwise `422 UnsupportedFormat`.
   145	- `data` binds parameter values declared by the template's `params:` (content, layout, styling, and conditional switches).
   146	- `?format=png|pdf` (default `png`) selects the output: `image/png` (rasterized at the template DPI) or
   147	  `application/pdf` (vector). An unknown value is `400 InvalidRequest`. The output is the raw image/PDF,
   148	  not a ZIP.
   149	- `?color_mode=color|bilevel` (default `color`): post-processing applied to the PNG raster after Typst
   150	  renders it. `bilevel` converts the image to pure 1-bit black/white by applying a global luminance
   151	  threshold (no dithering in this slice); it is useful for preparing a download that matches what a
   152	  bilevel printer will produce. `bilevel` is PNG-only: combining `format=pdf` with
   153	  `color_mode=bilevel` is `400 InvalidRequest`. Requires `format=png` (explicit or default). See
   154	  [ADR-0033](adr/0033-capability-aware-rendering.md) (this is slice 1; printer-driven color-mode and
   155	  resolution selection come in a later slice).
   156	- `?resolution=<dpi>` (default: the template `dpi` field): integer DPI override for the PNG raster. Lets
   157	  callers preview at a target device resolution without editing the template. Valid range is `[1, 1200]`;
   158	  a non-numeric value, `0`, or a value above `1200` is `400 InvalidRequest`. The value does not affect PDF
   159	  output (PDF is vector), but it is still validated, an out-of-range or non-numeric `resolution` is
   160	  rejected with `400` regardless of `format`. See [ADR-0033](adr/0033-capability-aware-rendering.md).
   161	
   162	### 2.2 `POST /batch`
   163	
   164	One endpoint for rendering and printing batches of labels. It owns the format decision so clients never
   165	branch on single vs. sheet: they post a list of resolved labels plus a `mode` and branch only on the
   166	response (download yields a binary, print yields a JSON summary). See [ADR-0011](adr/0011-unified-batch-endpoint.md).
   167	
   168	```json
   169	{
   170	  "template": "avery5163_asset_tag",
   171	  "mode": "download",
   172	  "start_slot": 0,
   173	  "labels": [
   174	    { "data": { "orientation": "horizontal", "show_border": "true", "id": "A1", "url": "https://example.com/A1", "name": "…", "tags": "…", "description": "…" } }
   175	  ]
   176	}
   177	```
   178	
   179	- `mode` is `download` or `print`. `print` requires `printer` and rejects `format` (`400 InvalidRequest`).
   180	- `format` (`png`|`pdf`) applies to single+download and selects the per-file render format. Sheet output
   181	  is always PDF, so `format` is ignored for sheet templates.
   182	- `start_slot` (default `0`) applies to sheet templates only: it is the zero-based index of the first
   183	  slot on the first page. Supplying it for a single template is `400 InvalidRequest`.
   184	- `printer` names a registered printer for `print` mode (unknown printer → `404`).
   185	
   186	`start_slot` is the first **job option**: a job-level knob intrinsic to the template's format (distinct
   187	from per-row `data` parameters), passed as an optional `/batch` field and validated
   188	against the format. Future job options (skip arbitrary sheet slots, per-job margins, continuous-tape
   189	cut/gap) follow the same pattern and are catalogued in [ADR-0012](adr/0012-job-options.md); none are
   190	implemented yet.

     1	# 6. Template edit ownership: manual vs GUI
     2	
     3	**Status:** Accepted
     4	
     5	## Context
     6	
     7	Templates are authored two ways: hand-written YAML (git-friendly, comment-rich, the artifact users
     8	version and share) and, once built, a WYSIWYG GUI editor (ADR pending for the editor stack). The GUI
     9	keeps the YAML layout tree as its source of truth and serializes back to YAML on save. That round-trip
    10	is lossy: standard YAML emitters strip comments and normalize key order, so a GUI save would silently
    11	destroy a hand-authored template's comments and formatting. The GUI also needs design-time-only data
    12	(sample/preview values for bound fields) that must not pollute the canonical template the renderer
    13	consumes. Allowing both editors to write the same file makes the file's content depend on which tool
    14	touched it last, which is the drift the source-of-truth principle (see the editor design) exists to
    15	prevent.
    16	
    17	## Decision
    18	
    19	Make edit ownership a property of each template; never allow two editors to write the same file.
    20	
    21	- A template is either **manual** (file-authored; the GUI may render, print, and preview it but not
    22	  edit it) or **gui** (GUI-owned; the GUI is its only editor).
    23	- Ownership is determined by location: manual templates live in `templates/`, GUI-owned templates in a
    24	  separate writable store (`templates-gui/`). Both classes are YAML files in the same schema and feed
    25	  one registry. For v1 the substrate is folders, not a database; app state (printers, settings, jobs)
    26	  is the thing that warrants SQLite, not templates.
    27	- A one-way **"Convert to GUI edit"** action *moves* a manual template into the GUI store and marks it
    28	  GUI-owned. It is a move, not a copy, so there is never a duplicate id or two diverging sources. The
    29	  reverse direction is a plain "export YAML" download; re-adopting it as manual is a manual file drop,
    30	  not an automatic round-trip.
    31	- Design-time-only data lives in an optional top-level `editor` block in the YAML, owned by the GUI and
    32	  ignored by the renderer. Because the renderer's parser uses `deny_unknown_fields`, this block must be
    33	  added to the schema explicitly. It only ever appears on GUI-owned templates.
    34	
    35	## Consequences
    36	
    37	- The lossy-round-trip problem disappears by construction: the GUI never rewrites a manually-owned
    38	  file, so comments and formatting in `templates/` are safe.
    39	- Both classes render and print identically; ownership gates editing only. The UI shows manual
    40	  templates with a lock badge and the "Convert to GUI edit" action.
    41	- The registry must scan both stores and still reject duplicate ids across them; the move semantics
    42	  keep this from happening in normal use.
    43	- Adding the `editor` block touches the schema (`raw.rs`, `models.rs`, the `TryFrom`) per ADR-0002,
    44	  and the renderer must skip it.
    45	- Converting is intentionally one-way and slightly inconvenient in reverse; this is the cost of keeping
    46	  a single source of edits.

    94	    onSuccess: async (_data, { id, yaml }) => {
    95	      qc.invalidateQueries({ queryKey: ["templates"] });
    96	      qc.invalidateQueries({ queryKey: ["template", id] });
    97	      // Cancel first: a failed save removes the source query, and the refetch that follows can still
    98	      // be in flight when a corrected save lands. Its older response would otherwise resolve after
    99	      // this write and clobber the YAML we know the server just stored.
   100	      await qc.cancelQueries({ queryKey: ["template-source", id] });
   101	      // setQueryData, not invalidateQueries: the value is known rather than merely stale, and an
   102	      // invalidated query keeps serving the old text while it refetches — long enough for a quick
   103	      // second Edit to seed from pre-save YAML (#141).
   104	      qc.setQueryData(["template-source", id], yaml);
   105	    },
   106	    // A failed PUT does not imply an unchanged file: the write lands before the reload, so a 500
   107	    // from the reload leaves the edit on disk while the cache holds the pre-edit text. Neither
   108	    // value is trustworthy, so drop it and let /source say what is stored.
   109	    onError: (_err, { id }) => {
   110	      qc.removeQueries({ queryKey: ["template-source", id] });
   111	    },
   112	  });

## Findings

### Critical (blocking)
none

### Moderate

**Move spec overpromises patchability for valid YAML templates without a line-oriented root mapping**  
Evidence: `openspec/changes/issue-164-template-groups/specs/template-groups/spec.md:166-169` requires inserting a `group:` line when none exists while preserving every other byte. `openspec/changes/issue-164-template-groups/design.md:110-125` only defines finding column-0 block-style key lines and inserting after `name:`, `id:`, or the document header. Current parsing does not constrain authors to block-style root mappings: `docs/SPEC.md:286-304` says templates are YAML files with top-level fields, and `src/parse.rs:25-31` deserializes YAML into `TemplateDefinitionRaw` without recording YAML style.  
Why wrong: a valid YAML template encoded as a top-level flow mapping with no `group` has no line after `name:`/`id:` to patch and no safe single-line insertion point that preserves every other byte. The implementation would either return `422` despite the spec saying it inserts when none exists, or risk producing invalid/corrupted YAML.  
Fix: explicitly refuse root documents that are not a block mapping with a safe top-level insertion point, and add a scenario such as “top-level flow mapping without `group` is `422` and unchanged.”

**OpenAPI contract is incomplete for the new API surface**  
Evidence: the spec requires OpenAPI to describe `group` only on schemas at `openspec/changes/issue-164-template-groups/specs/template-groups/spec.md:99`, but the same spec adds `GET /api/templates?group=` at `spec.md:118-123` and `PUT /api/templates/{id}/group` at `spec.md:163-197`. The proposal’s impact already expects OpenAPI work for “the new parameter, request body, and route” at `proposal.md:52-54`.  
Why wrong: the normative spec makes the new query parameter and move endpoint part of the API, but does not require `GET /api/openapi.json` to expose them. That leaves generated clients and Swagger users unable to discover the main new write path even if implementation behavior is correct.  
Fix: add OpenAPI SHALLs to the filter and move requirements: document the `group` query parameter, the `PUT /templates/{id}/group` route, its request body, responses, and any new error reasons.

**Design goal contradicts the specified invalid-group behavior**  
Evidence: `openspec/changes/issue-164-template-groups/design.md:28` says “Nothing about grouping can take the service down or make a template unrenderable.” The spec says an invalid `group` makes the template fail to load and be quarantined at `spec.md:25-28`. The existing registry spec says refused files are excluded from the served set at `openspec/specs/template-registry/spec.md:8-14`.  
Why wrong: a hand-authored invalid `group:` absolutely can make that template unrenderable by excluding it from the registry. The intended invariant appears to be narrower: invalid group content must not abort startup, and the move endpoint must not write invalid content.  
Fix: rewrite the goal/risk wording to match the contract: grouping faults quarantine only the bad file, and group moves validate before writing.

### Suggestions

**Define group sort order mechanically**  
Evidence: group names are case-sensitive at `spec.md:30`, while the Labels view lists groups in “ascending order” at `spec.md:271`.  
Why it matters: `Warehouse`, `warehouse`, accented names, and punctuation can sort differently depending on locale/API choices.  
Fix: specify the collation used for group chips, for example Unicode code point order or the same comparator the implementation will test.

**Add patcher tests for comment-like characters inside quoted values**  
Evidence: the move patch must preserve comments and other bytes at `spec.md:166-169`, and the design says it re-attaches trailing comments at `design.md:121-122`.  
Why it matters: `group: "A # B" # real comment` requires distinguishing `#` inside a quoted scalar from a real YAML comment.  
Fix: include explicit tests/scenarios for quoted group values containing `#` and `:` plus a trailing comment.
