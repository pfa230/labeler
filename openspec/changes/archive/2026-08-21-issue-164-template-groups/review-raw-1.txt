## Templates are visual artifacts

A YAML edit that parses and renders without error is not proof the label looks right. Use a
render → inspect → fix loop: render to PNG (`POST /api/render/label?format=png`, with
`LABELER_NO_AUTH=true` locally), **open the image** and check it against intent (QR squareness, text
inside the printable area, alignment, auto-shrink, no clipping), fix the YAML, and re-render
(`POST /api/templates/reload` picks up edits without a restart). Stop when it is correct, not when it
merely renders. See #67.

## Architecture

Request path `api.rs → render/`; template path `templates.rs → parse.rs → raw.rs → convert.rs`.

- **Two-stage parsing.** YAML deserializes into `raw.rs` structs (all `deny_unknown_fields`), then
  converts to the domain model via `TryFrom` in `convert.rs`, with `serde_path_to_error` attaching a
  JSON path to every error. This lets the wire format differ from the validated model. *Adding a
  layout field means editing three files together: `raw.rs`, `models.rs`, `convert.rs`.*
- **Template registry.** Loaded and `validate()`d at startup (`main.rs`). A template that fails to
  parse or validate is **quarantined** and the server still starts (#175); so is a file whose id is
  already taken, with the lexicographically first filename keeping the id (#181, ADR-0058). No
  template content is fatal. Nothing is seeded into a fresh config dir. Templates are immutable,
  shared via `Arc`.
- **Layout model** (`models.rs`). `layout` is a tree of `LayoutItem`s: `Text`, `Qr`, `Image`, `Line`,
  `Container`. `Container` nests `items` recursively and may carry `frame` and `padding`. Any item may
  carry `when:`, the universal conditional-visibility predicate over `params` (ADR-0056, #162).
  Write new templates with `params` + `when`, but note the legacy top-level `options:` map and
  `container.option` still **parse**: they desugar into an enum `params` entry and into `when`
  (`convert.rs:284`, `convert.rs:107`). Do not treat a template using them as invalid.
- **Coordinates.** Bottom-left origin, y-up, in the template `unit` (`mm` or `in`). Typst is top-left,
  so the renderer flips with `frame_height_units - top`. A `Container` re-bases children into its
  padded inner box via a fresh `RenderContext`. *Watch this when touching placement math.*
- **Sizing.** `size` is a number or `auto`. `auto` resolves to `max_w`/`max_h` if given, else (for
  containers and lines) the parent frame. *This logic is duplicated between compile-time validation
  (`templates.rs`) and render-time resolution (`render/mod.rs`); keep the two in sync.*
- **Rendering** (`render/mod.rs`). Walks the layout emitting Typst markup; PNG via `typst-render`,
  sheets as one clipped box per slot via `typst-pdf`. `render/helpers.rs` holds string escaping,
  length formatting, QR-SVG generation (`qrcode`), and `ttf-parser`-based text fitting for
  `font_size: {min, max}` (auto-shrink plus ellipsis truncation).
- **Errors.** `TemplateError` (parse/validation, carries a path) quarantines rather than aborting
  startup. `AppError` is the HTTP error, serializing to `{ "error": { code, message, details } }`. Add
  new kinds as `AppError` constructors so `code` strings stay stable.
- **OpenAPI.** Every model exposed in the API must be registered in `src/openapi.rs`.

`GET /api/templates` returns every template sorted by id, and the Labels page renders them as one

## What Changes

- **Template schema.** A new optional top-level `group:` string. One flat level, no separator
  semantics: `Electronics / Cables` is a name, not a path. A template without the key is *ungrouped*,
  which stays the default for every template that exists today.
- **API.** `group` is exposed on `TemplateSummary` and `TemplateDetail`. `GET /api/templates` gains a
  `group` query parameter: absent lists everything, `?group=<name>` lists exact matches, `?group=`
  (present, empty) lists the ungrouped ones.
- **New endpoint.** `PUT /api/templates/{id}/group` sets or clears one template's group by rewriting
  the single `group:` line of its file, leaving every other byte, comments included, untouched. This
  is what the UI's move action calls; it is a deliberate, narrow exception to the no-machine-writes
  rule of ADR-0006, and gets its own ADR.
- **Web UI.** The Labels page gains a group filter row (`All`, each group, `Ungrouped`) that composes
  with the existing search box, a per-card **Move to…** action, and a checkbox multi-select for
  moving several cards at once. The move dialog is a combobox over the groups in use where typing an
  unused name creates it. No group is ever typed into YAML to be assigned, and no client code
  rewrites template source.
- **Docs.** `docs/AUTHORING.md` documents the field. Two ADRs: the group model (YAML-native, flat),

## Purpose

Defines how a template declares the group it belongs to, what a valid group name is, how groups reach
the API on template summaries and detail, how the template list is filtered by group, how a template
is moved from one group to another without disturbing the rest of its file, and how groups are
browsed in the Labels view.

## ADDED Requirements

### Requirement: A template declares its group as an optional top-level field

A template MAY carry a top-level `group` field naming the one group it belongs to. The field is
optional; a template without it is *ungrouped*, and ungrouped is a first-class state, not an error.

A group name is one flat name. The service SHALL NOT assign meaning to any character inside it: a
name containing `/` is a name, not a path, and produces no hierarchy.

A `group` value SHALL be valid when, after stripping leading and trailing whitespace, it is:

- a string;
- non-empty;
- at most 64 characters;
- free of control characters, including tab, carriage return, and line feed.

The stored group is the whitespace-stripped value. A `group` that is not a string, is empty or
whitespace-only, exceeds 64 characters, or carries a control character SHALL make the template fail
to load, with a parse or validation message naming the `group` field. That quarantines the file
under the existing rules of the `template-registry` capability rather than aborting startup.

Group names SHALL be compared exactly, including case: `Warehouse` and `warehouse` are two groups.

The post-change set of top-level template fields is:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Required, non-empty. Uniqueness across the directory is enforced per `template-registry`. |
| `name` | string | Required, non-empty. |
| `description` | string | Optional. |
| `group` | string | Optional. One flat group name, validated as above. Absent means ungrouped. |
| `unit` | `"mm"` \| `"in"` | Length unit for all coordinates/sizes in the template. |
| `dpi` | integer > 0 | Raster resolution for PNG output. |
| `format` | object | See `docs/SPEC.md` §3.1. |
| `params` | map | Optional. Map of parameter name → `ParamSpec`. See `docs/SPEC.md` §3.0. |
| `layout` | list | Tree of layout items. See `docs/SPEC.md` §4. |
| `version` | string | Optional, free-form. |

Parsing still rejects unknown fields.

This requirement supersedes the `docs/SPEC.md` §3 top-level field table, and only that table. Every
other rule in §3, and the frozen §3.0 and §3.1 subsections, stay authoritative.

#### Scenario: A template carries a group

- **WHEN** a template file declares `group: Warehouse` and is otherwise valid
- **THEN** the template loads
- **AND** its group is `Warehouse`

#### Scenario: A template without the field is ungrouped

- **WHEN** a valid template file declares no `group` key
- **THEN** the template loads
- **AND** it is reported as ungrouped, not as broken

#### Scenario: Surrounding whitespace is not part of the name

- **WHEN** a template declares `group: "  Warehouse  "`
- **THEN** its group is `Warehouse`

#### Scenario: An empty group name is a validation failure

- **WHEN** a template declares `group: ""` or a whitespace-only value
- **THEN** the template fails to load, with a message naming `group`
- **AND** the file is quarantined as broken while the service keeps running

#### Scenario: An over-long or control-character name is a validation failure

- **WHEN** a template declares a `group` longer than 64 characters, or one containing a line feed
- **THEN** the template fails to load, with a message naming `group`

#### Scenario: A slash produces no hierarchy

- **WHEN** two templates declare `group: Shipping/Pallets` and `group: Shipping`
- **THEN** they belong to two unrelated groups
- **AND** neither is nested inside the other

### Requirement: Group is exposed on template summaries and detail

`GET /api/templates` SHALL carry each template's `group` in its summary, and `GET /api/templates/{id}`
SHALL carry it in the detail. The field SHALL be omitted from the response body when the template is
ungrouped, so an existing consumer sees exactly the payload it saw before this change.

The `broken` list of `GET /api/templates` SHALL be unchanged: a refused file is reported as
`{ filename, error }` whether or not it declares a group, since a file that failed to load has no
group to report.

The OpenAPI document at `GET /api/openapi.json` SHALL describe `group` on both schemas.

This requirement supersedes the `docs/SPEC.md` §2 endpoint-table success column for
`GET /api/templates` and `GET /api/templates/{id}` as to response content, and adds `group` to the
template payloads described in §2.0. It changes nothing else about those endpoints: the list stays
sorted by id, and detail still carries the full layout.

#### Scenario: A grouped template reports its group

- **WHEN** `GET /api/templates` is called and one template declares `group: Warehouse`
- **THEN** that template's summary carries `group` with the value `Warehouse`

#### Scenario: An ungrouped template omits the field

- **WHEN** `GET /api/templates/{id}` is called for a template that declares no group
- **THEN** the response body contains no `group` key

### Requirement: The template list filters by group

`GET /api/templates` SHALL accept an optional `group` query parameter:

- **absent** — every template is listed, grouped and ungrouped alike;
- **`?group=<name>`** — only templates whose group equals `<name>` exactly, after the same
  whitespace stripping applied to the stored value;
- **`?group=`**, present with an empty value — only ungrouped templates.

A `group` naming no existing group SHALL return `200` with an empty `templates` list, never `404`.

Filtering SHALL NOT change the order of the results, which stays ascending by id, and SHALL NOT
change the `broken` list, which continues to report every refused file regardless of the filter,
because a refused file has no group to filter on.

### Requirement: A template is moved between groups without rewriting the rest of its file

`PUT /api/templates/{id}/group` SHALL set or clear one template's group. The request body is
`{ "group": "<name>" }` to move it into a group, or `{ "group": null }` to make it ungrouped.

The service SHALL apply the change as a targeted edit of the stored file: it replaces the value of
the existing top-level `group:` line, or, when there is none, inserts one. Every other byte of the
file SHALL be preserved exactly, including comments, key order, indentation style, quoting of other
values, and blank lines. Clearing a group SHALL remove the whole `group:` line.

The patched text SHALL be parsed and validated before anything is written, and SHALL be written only
if it is a valid template whose group reads back as the requested value. The file SHALL be replaced
atomically, and the registry reloaded, exactly as the other template writes do.

The service SHALL refuse, with nothing written, a file it cannot patch unambiguously: one holding
more than one YAML document, or whose top-level `group` value is not a plain scalar. A `group:` key
that is not top-level, such as one inside `params` or a layout item, SHALL be left alone and SHALL
NOT be mistaken for the template's group.

Responses:

| Status | Meaning |
| --- | --- |
| `200` | Moved. Body is the updated `TemplateDetail`. |
| `400` | The path id is invalid, or the body is not `{ "group": string \| null }`. |
| `404` | The registry holds no template with that id. |
| `422` | The group name fails validation, or the file cannot be patched unambiguously. |
| `500` | The file could not be written, or the directory could not be re-read afterwards. |

The operation SHALL be idempotent: setting the group a template already has, or clearing an already
ungrouped template, SHALL return `200` and leave the file byte-identical.

This endpoint SHALL be the only path by which the service writes a group into a hand-authored file.
`PUT /api/templates/{id}` continues to replace the whole file from a submitted body, and a `group:`
key typed there is honoured exactly like any other field.

   109	
   110	#### Scenario: An invalid body is rejected before the write
   111	
   112	- **WHEN** `PUT /api/templates/{id}` receives a body that fails validation
   113	- **THEN** the response is `422`
   114	- **AND** the stored file is unchanged
   115	
   116	#### Scenario: A refused sibling does not block a delete
   117	
   118	- **WHEN** `DELETE /api/templates/{id}` is called on a served template while another file in the directory is refused
   119	- **THEN** the response is `204`
   120	- **AND** the refused file is still reported as broken

    85	### 2.0 Template management
    86	
    87	Templates are hand-authored YAML in the templates dir and may also be managed over the API. The
    88	registry is held in an `ArcSwap` for lock-free reads; `reload` and every mutation rebuild it from disk
    89	and swap atomically. A reload that fails (an invalid file on disk) returns `422` and keeps the
    90	previously-loaded set, so a bad file never takes the service down.
    91	
    92	- `POST /templates/reload` re-scans the dir and returns `{ "count": N }`.
    93	- `POST /templates` creates from a raw YAML body; the `id` comes from the body; `409 Conflict` if it
    94	  already exists.
    95	- `PUT /templates/{id}` replaces from a raw YAML body; the body `id` must equal the path `{id}` (else
    96	  `400`); `404` if it does not exist. A `422` has two sources and they differ in effect: the submitted
    97	  body failing `parse_and_validate`, which is rejected before anything is written, or the directory
    98	  reload that *follows* a successful write finding some other template invalid — in which case the
    99	  file has already been replaced while the registry keeps the previous set, and retrying the save once
   100	  the directory is valid converges. Callers must not read a `422` as "nothing was saved".
   101	- `DELETE /templates/{id}` removes the template's backing file and returns `204`; `400` on an invalid
   102	  id, `404` when the registry holds no such id, `422` when the file was removed but reloading the
   103	  directory then found some *other* template invalid (the previous set stays live, so the deleted id
   104	  lingers in memory until a later reload succeeds; retrying the delete once the directory is fixed
   105	  converges). The delete is permanent: nothing re-seeds templates
   106	  (the binary has shipped none since #137), so a deleted template does not return on restart. It also
   107	  drops every user's favorite for that id, so a later template reusing the id does not inherit them.
   108	  Recents are left alone: they derive from the print-job log, and deleting a template must not erase
   109	  the record that labels were printed from it (ADR-0048).
   110	- `GET /templates/{id}/source` returns the raw stored YAML (`text/yaml`) for the read-only source view;
   111	  `400` on an invalid id, `404` if the file is missing.
   112	- `GET /templates/{id}/thumbnail` renders a representative PNG for the template using placeholder data
   113	  (each field filled with its field name, each QR code encoded with its field name). For `single`
   114	  templates it renders the one label. For `sheet` templates it renders a single label slot (not a full
   115	  sheet) so the preview is label-sized regardless of format. Variables (`{vars.X}`) are resolved from
   116	  the store; undefined variable references cause a `422`. The default option selection (first allowed
   117	  value per option key) is used automatically. The response carries `ETag` (a quoted SHA-256 of the
   118	  rendered PNG bytes, so it moves with the template, the renderer, the interpolated variables and the
   119	  datetime formats alike; #129) and `Cache-Control: no-cache`; callers that send `If-None-Match` with a matching ETag
   120	  receive `304 Not Modified`. Error codes: `404 TemplateNotFound` for unknown ids, `422` for
   121	  render/interpolation failures.
   122	
   123	The CSV Import and Homebox Connect pages render an on-demand, selected-row preview using the same
   124	endpoints: `POST /render/label` for single templates, `POST /batch` (mode `download`, one label) for
   125	sheet templates. The preview reuses the full option-resolution path (the same one download/print use),
   126	so the preview matches the actual rendered output. A preview failure (non-2xx) surfaces inline in the
   127	`PreviewPane` and never disables Download or Print.
   128	
   129	API-managed templates are written as `<id>.yaml` under the templates dir (atomic temp-then-rename), and
   130	`id` must contain only letters, digits, `-`, or `_` (path-traversal guard). Parse errors and validation
   131	failures return `422 TemplateInvalid` with a path-aware message; the GUI-owned store is Phase 2
   132	(ADR-0006).

   134	### 2.1 `POST /render/label`
   135	
   136	```json
   137	{
   138	  "template": "brother_18mm_qr",
   139	  "data": { "message": "Hello", "code": "QR-123" }
   140	}
   141	```
   142	
   143	- Renders a single label as a preview or one-off; for multi-label work and printing, use `POST /batch`.
   144	- `template` must reference a template whose `format.type` is `single`; otherwise `422 UnsupportedFormat`.
   145	- `data` binds parameter values declared by the template's `params:` (content, layout, styling, and conditional switches).
   146	- `?format=png|pdf` (default `png`) selects the output: `image/png` (rasterized at the template DPI) or
   147	  `application/pdf` (vector). An unknown value is `400 InvalidRequest`. The output is the raw image/PDF,
   148	  not a ZIP.
   149	- `?color_mode=color|bilevel` (default `color`): post-processing applied to the PNG raster after Typst
   150	  renders it. `bilevel` converts the image to pure 1-bit black/white by applying a global luminance
   151	  threshold (no dithering in this slice); it is useful for preparing a download that matches what a
   152	  bilevel printer will produce. `bilevel` is PNG-only: combining `format=pdf` with
   153	  `color_mode=bilevel` is `400 InvalidRequest`. Requires `format=png` (explicit or default). See
   154	  [ADR-0033](adr/0033-capability-aware-rendering.md) (this is slice 1; printer-driven color-mode and
   155	  resolution selection come in a later slice).
   156	- `?resolution=<dpi>` (default: the template `dpi` field): integer DPI override for the PNG raster. Lets
   157	  callers preview at a target device resolution without editing the template. Valid range is `[1, 1200]`;
   158	  a non-numeric value, `0`, or a value above `1200` is `400 InvalidRequest`. The value does not affect PDF
   159	  output (PDF is vector), but it is still validated, an out-of-range or non-numeric `resolution` is
   160	  rejected with `400` regardless of `format`. See [ADR-0033](adr/0033-capability-aware-rendering.md).
   161	
   162	### 2.2 `POST /batch`
   163	
   164	One endpoint for rendering and printing batches of labels. It owns the format decision so clients never
   165	branch on single vs. sheet: they post a list of resolved labels plus a `mode` and branch only on the
   166	response (download yields a binary, print yields a JSON summary). See [ADR-0011](adr/0011-unified-batch-endpoint.md).
   167	
   168	```json
   169	{
   170	  "template": "avery5163_asset_tag",
   171	  "mode": "download",
   172	  "start_slot": 0,
   173	  "labels": [
   174	    { "data": { "orientation": "horizontal", "show_border": "true", "id": "A1", "url": "https://example.com/A1", "name": "…", "tags": "…", "description": "…" } }
   175	  ]
   176	}
   177	```
   178	
   179	- `mode` is `download` or `print`. `print` requires `printer` and rejects `format` (`400 InvalidRequest`).
   180	- `format` (`png`|`pdf`) applies to single+download and selects the per-file render format. Sheet output
   181	  is always PDF, so `format` is ignored for sheet templates.
   182	- `start_slot` (default `0`) applies to sheet templates only: it is the zero-based index of the first
   183	  slot on the first page. Supplying it for a single template is `400 InvalidRequest`.
   184	- `printer` names a registered printer for `print` mode (unknown printer → `404`).
   185	
   186	`start_slot` is the first **job option**: a job-level knob intrinsic to the template's format (distinct
   187	from per-row `data` parameters), passed as an optional `/batch` field and validated
   188	against the format. Future job options (skip arbitrary sheet slots, per-job margins, continuous-tape
   189	cut/gap) follow the same pattern and are catalogued in [ADR-0012](adr/0012-job-options.md); none are
   190	implemented yet.
   191	
   192	**Dispatch matrix** (by template `format.type` × `mode`):
   193	
   194	| | `download` | `print` |
   195	| --- | --- | --- |
   196	| `single` | ZIP of per-label files (`application/zip`), one per label in the `format` render format | one print job per label |
   197	| `sheet` | labels laid into slots, paginated across pages, as one `application/pdf` | that paginated PDF sent as a single print job |
   198	
   199	**Validate-then-execute.** Every label is render-validated first. If any label has bad data, the request
   200	returns `422 BatchInvalid` with `details.failures: [{ index, code, reason?, message }]` listing every
   201	failing label, and nothing is produced or printed (atomic in both modes and both formats). `reason` is
   202	present exactly when that failure's `code` is one that carries a reason (§10.1) and is omitted
   203	otherwise. Only once all labels
   204	validate does the endpoint execute: `download` streams the blob; `print` dispatches jobs and returns a
   205	`200` summary.
   206	
   207	**Print summary (`BatchSummary`).** Print transport is best-effort: a label that fails to send is
   208	reported, not fatal.
   209	
   210	```json
   211	{ "total": 3, "succeeded": 2, "failed": [{ "index": 1, "error": "…" }], "jobs": 1 }
   212	```
   213	
   214	`jobs` counts jobs dispatched: one per label for single templates, `1` for a sheet (the whole sheet is
   215	one job). `failed[].index` is the zero-based label index.
   216	
   217	- Batches over 500 labels return `413 BatchTooLarge`.
   218	- `template` referencing an unknown id → `404`; parameter values in `data` are validated against the template's declared `params`.

   220	### 2.3 `POST /print`
   221	
   222	An inbound print webhook for integrations (Grocy, scripts, local automation). It prints one label,
   223	optionally repeated, to a named printer. See [ADR-0031](adr/0031-inbound-print-webhook.md) and [ADR-0055](adr/0055-parameterized-templates.md).
   224	
   225	```json
   226	{
   227	  "template": "brother_24mm",
   228	  "printer":  "office",
   229	  "data":     { "name": "Tomato Soup", "qty": "3", "orientation": "horizontal" },

   231	}

   233	
   234	| Field | Type | Required | Notes |
   235	| --- | --- | --- | --- |
   236	| `template` | string | Yes | Template id; `404` if not found. |
   237	| `printer` | string | Yes | Printer id; `404` if not found. |
   238	| `data` (or `fields`) | object | No (defaults to `{}`) | Parameter map passed to the template. `fields` is accepted as a legacy synonym. |
   239	| `copies` | integer 1..100 | No | Number of label instances to print (default `1`). |
   240	
   241	`copies` counts **label instances**, not printer copies. A value of 2 sends two identical labels: two
   242	separate print jobs for `single`/tape templates, or two slots on a sheet (paginated like `/batch`).

   244	
   245	**Response.** Always `BatchSummary` on success:
   246	
   247	```json
   248	{ "total": 2, "succeeded": 2, "failed": [], "jobs": 2 }

   251	(`jobs: 2` is for a `single`/tape template with `copies: 2`; a `sheet` template would report `jobs: 1`.)
   252	
   253	`total` and `succeeded` count label instances (copies). `jobs` counts actual printer dispatches: equal
   254	to `copies` for `single`/tape templates; fewer for `sheet` templates (the sheet is paginated and sent

   265	| 409 | `MediaMismatch` | Template `media_width` and the printer's loaded media width differ by more than 1 mm (preflight gate). |
   266	| 413 | `PayloadTooLarge` | Request body exceeds 64 KiB. |

   268	| 502 | `PrintFailed` | Pre-send dispatch failure (before any job is accepted). |

   284	## 3. Template schema
   285	
   286	Templates are `*.yaml` / `*.yml` files in the templates directory (`{config}/templates/`, where
   287	`{config}` is `LABELER_CONFIG_DIR`). A file's name need not match the `id` inside it: the registry
   288	keys on the `id` and remembers which file each id came from, and `GET /templates/{id}/source`, `PUT`
   289	and `DELETE` act on that file. `POST /templates` writes a new template as `{id}.yaml`. Top-level
   290	fields:
   291	
   292	| Field | Type | Notes |
   293	| --- | --- | --- |
   294	| `id` | string | Required, non-empty, unique across the directory. |
   295	| `name` | string | Required, non-empty. |
   296	| `description` | string | Optional. |
   297	| `unit` | `"mm"` \| `"in"` | Length unit for all coordinates/sizes in the template. |
   298	| `dpi` | integer > 0 | Raster resolution for PNG output. |
   299	| `format` | object | See §3.1. |
   300	| `params` | map | Optional. Map of parameter name → `ParamSpec`. See §3.0. |
   301	| `layout` | list | Tree of layout items. See §4. |
   302	| `version` | string | Optional, free-form. |

   304	Parsing rejects unknown fields (`deny_unknown_fields`). An invalid template aborts server startup.

   309	styling parameters, and conditional switches (ADR-0055).

   311	```yaml
   312	params:

   314	    type: string
   315	    description: "Main label text"
   316	    multiline: false
   317	  notes:
   318	    type: string
   319	    multiline: true
   320	    default: ""
   321	  target_width:
   322	    type: length
   323	    default: 80
   324	    min: 25
   325	    max: 300
   326	    description: "Target length"
   327	  weight:
   328	    type: integer
   329	    default: 400
   330	    enum: [100, 200, 300, 400, 500, 600, 700, 800, 900]
   331	  show_border:
   332	    type: boolean
   333	    default: false
   334	  orientation:
   335	    type: enum
   336	    values: [horizontal, vertical]
   337	    default: horizontal
   338	```

   340	**Parameter types and attributes:**
   341	
   342	| Type | YAML Attributes | Request Value | Behavior when Omitted from Request | UI Form Control |
   343	| --- | --- | --- | --- | --- |
   344	| `string` | `default`, `multiline` (bool), `description` | String scalar | If `default` set: uses `default`. If no `default`: `422 MissingField` when rendered in active layout. | Text input (`multiline: false`) or Textarea (`multiline: true`) |
   345	| `length` | `default`, `min`, `max`, `description` | Number or dimension string (`80`, `"80mm"`) | If `default` set: uses `default`. If no `default`: `422 MissingField` when active. | Number input with unit suffix, or Slider (if `min`/`max` provided) |
   346	| `integer` | `default`, `min`, `max`, `enum` (list), `description` | Integer (`400`) | If `default` set: uses `default`. If no `default`: `422 MissingField` when active. | Number input / Stepper / Dropdown (if `enum` provided) |
   347	| `number` | `default`, `min`, `max`, `description` | Float / number (`1.5`) | If `default` set: uses `default`. If no `default`: `422 MissingField` when active. | Number input with step |
   348	| `boolean` | `default`, `description` | `true` / `false` | If `default` set: uses `default`. If no `default`: `false`. | Toggle switch / Checkbox |
   349	| `enum` | `values` (required list), `default`, `description` | String matching `values` | If `default` set: uses `default`. If no `default`: first value in `values`. | Dropdown / Segmented button group |

   352	- Parameter names must match `^[a-zA-Z0-9_-]+$`.

   355	### 3.1 `format`
   356	
   357	Tagged by `type`:
   358	
   359	**`single`** — one label of possibly dynamic size:
   360	
   361	```yaml
   362	format:

   364	  width: { min: 10.0, max: "{target_width}" }   # Dynamic Dimension referencing parameter

   367	```
   368	
   369	| Field | Type | Required | Notes |
   370	| --- | --- | --- | --- |

    66	/// Every entry of `dir`, sorted. Loading in sorted order rather than `read_dir` order is what makes
    67	/// the winner of an id collision a property of the directory contents instead of a property of this
    68	/// filesystem's enumeration (#181). Every path shares the same parent, so ordering by path is
    69	/// ordering by filename.
    70	fn sorted_dir_paths(dir: &FsPath) -> Result<Vec<PathBuf>, TemplateRegistryError> {
    71	    let entries = std::fs::read_dir(dir).map_err(|source| TemplateRegistryError::Io {
    72	        path: dir.to_path_buf(),
    73	        source,
    74	    })?;
    75	    let mut paths = Vec::new();
    76	    for entry in entries {
    77	        let entry = entry.map_err(|source| TemplateRegistryError::Io {
    78	            path: dir.to_path_buf(),
    79	            source,
    80	        })?;
    81	        paths.push(entry.path());
    82	    }
    83	    paths.sort();
    84	    Ok(paths)
    85	}

   114	                        source,

   149	                    id: template.id.clone(),
   150	                    first: existing_path.clone(),
   151	                    second: path,

   155	                broken.push(BrokenTemplate { filename, error });
   156	                continue;
   157	            }

   161	                template.id.clone(),
   162	                hex::encode(Sha256::digest(contents.as_bytes())),
   163	            );
   164	            templates.insert(template.id.clone(), template);
   165	        }

   169	            hashes,

   310	fn template_file_path(dir: &std::path::Path, id: &str) -> Result<PathBuf, AppError> {
   311	    if id.is_empty()
   312	        || !id
   313	            .chars()

   326	/// The on-disk file backing `id`, per the registry. `None` for an id the registry does not hold.
   327	///
   328	/// It resolves through the registry and never guesses at a filename: `y1.yml` may well declare
   329	/// `id: other`, so treating a matching filename as the backing file would let `DELETE /templates/y1`
   330	/// unlink another template's file. A stray file the registry never loaded stays a filesystem
   331	/// concern (#140).
   332	fn existing_template_file(
   333	    registry: &TemplateRegistry,
   334	    dir: &std::path::Path,
   335	    id: &str,
   336	) -> Result<Option<PathBuf>, AppError> {
   337	    // Called for its id validation; the conventional path it returns is not the answer here.
   338	    template_file_path(dir, id)?;
   339	    Ok(registry.path(id).map(std::path::Path::to_path_buf))
   340	}

   351	fn write_template_file(path: &std::path::Path, body: &str) -> Result<(), AppError> {
   352	    let dir = path.parent().ok_or_else(|| {
   353	        AppError::render_failed(Reason::TemplatePathInvalid, "invalid template path")
   354	    })?;
   355	    let file_name = path
   356	        .file_name()
   357	        .and_then(|name| name.to_str())
   358	        .ok_or_else(|| {
   359	            AppError::render_failed(Reason::TemplatePathInvalid, "invalid template path")
   360	        })?;
   361	    let nonce = std::time::SystemTime::now()
   362	        .duration_since(std::time::UNIX_EPOCH)
   363	        .map(|d| d.as_nanos())
   364	        .unwrap_or(0);
   365	    let tmp = dir.join(format!(".{file_name}.{nonce}.tmp"));
   366	    std::fs::write(&tmp, body).map_err(|err| {
   367	        AppError::render_failed(
   368	            Reason::TemplateWriteFailed,
   369	            format!("failed to write template: {err}"),
   370	        )
   371	    })?;
   372	    std::fs::rename(&tmp, path).map_err(|err| {
   373	        AppError::render_failed(
   374	            Reason::TemplateWriteFailed,
   375	            format!("failed to persist template: {err}"),
   376	        )
   377	    })?;
   378	    Ok(())
   379	}

   391	pub async fn create_template(
   392	    State(state): State<Arc<AppState>>,
   393	    body: String,
   394	) -> Result<Response, AppError> {
   395	    let template = parse_and_validate(&body)?;
   396	    let id = template.id.clone();
   397	    let path = template_file_path(&state.templates_dir, &id)?;
   398	    let _guard = state.write_lock.lock().await;
   399	    // Registry first: the id may already be held by a file under a different name, which
   400	    // `path.exists()` misses. The path check still covers a file the registry has not loaded. Since
   401	    // #181 the reload below no longer fails on a duplicate id, so this guard is the only thing
   402	    // standing between a write and a silent collision, and it misses a file added to the directory
   403	    // since the last reload (#184).
   404	    if state.templates.load_full().get(&id).is_some() || path.exists() {
   405	        return Err(AppError::template_exists(&id));
   406	    }
   407	    write_template_file(&path, &body)?;
   408	    state.reload()?;
   409	    let detail = state.templates.load_full().detail(&id).ok_or_else(|| {
   410	        AppError::render_failed(
   411	            Reason::TemplateMissingAfterWrite,
   412	            "template missing after write",
   413	        )
   414	    })?;
   415	    Ok((axum::http::StatusCode::CREATED, Json(detail)).into_response())
   416	}

   431	    State(state): State<Arc<AppState>>,
   432	    Path(id): Path<String>,
   433	    body: String,
   434	) -> Result<Response, AppError> {
   435	    let template = parse_and_validate(&body)?;

   449	        .ok_or_else(|| AppError::template_not_found(id.clone()))?;
   450	    write_template_file(&path, &body)?;
   451	    state.reload()?;
   452	    let detail = state.templates.load_full().detail(&id).ok_or_else(|| {
   453	        AppError::render_failed(
   454	            Reason::TemplateMissingAfterWrite,
   455	            "template missing after write",
   456	        )
   457	    })?;

   472	pub async fn delete_template(
   473	    State(state): State<Arc<AppState>>,
   474	    Path(id): Path<String>,
   475	) -> Result<Response, AppError> {
   476	    let _guard = state.write_lock.lock().await;
   477	    let path = existing_template_file(&state.templates.load_full(), &state.templates_dir, &id)?
   478	        .ok_or_else(|| AppError::template_not_found(id.clone()))?;
   479	    match std::fs::remove_file(&path) {
   480	        Ok(()) => {}
   481	        // The registry can outlive the file: if a previous delete unlinked it but its `reload()`
   482	        // then failed on an unreadable directory, the old set stays live and still names this path.
   483	        // Treat an already-absent file as removed and carry on, so retrying the delete once the
   484	        // directory is readable converges instead of failing forever on a file that is already gone.
   485	        Err(err) if err.kind() == std::io::ErrorKind::NotFound => {}
   486	        Err(err) => {
   487	            return Err(AppError::render_failed(
   488	                Reason::TemplateDeleteFailed,
   489	                format!("failed to delete template: {err}"),
   490	            ))
   491	        }
   492	    }
   493	    // After the unlink, before the reload. Unlink first because it is the step that realistically
   494	    // fails, and a prune-first order would mean a failed unlink had already destroyed favorites for
   495	    // a template that still exists. Before the reload because `reload()` re-reads the whole
   496	    // directory and can still fail on an unreadable one (bad content is quarantined, I/O is not).
   497	    // With the prune after it, that failure would leave the file deleted and the favorite alive,
   498	    // the exact state this prune prevents.
   499	    // Recents are not pruned: they derive from the job log, which is print history (#94).
   500	    state.store().remove_favorites_for_template(&id).await?;
   501	    state.reload()?;
   502	    Ok(axum::http::StatusCode::NO_CONTENT.into_response())
   503	}

   570	    let template = registry
   571	        .get(&id)
   572	        .ok_or_else(|| AppError::template_not_found(id.clone()))?;
   573	    let data = crate::render::placeholder_data(template);
   574	    let option = crate::render::default_option_selection(template);
   575	    let variables = state.store().all_variables().await?;

   600	                .into_response());
   601	        }
   602	    }

     1	# 6. Template edit ownership: manual vs GUI
     2	
     3	**Status:** Accepted
     4	
     5	## Context
     6	
     7	Templates are authored two ways: hand-written YAML (git-friendly, comment-rich, the artifact users
     8	version and share) and, once built, a WYSIWYG GUI editor (ADR pending for the editor stack). The GUI
     9	keeps the YAML layout tree as its source of truth and serializes back to YAML on save. That round-trip
    10	is lossy: standard YAML emitters strip comments and normalize key order, so a GUI save would silently
    11	destroy a hand-authored template's comments and formatting. The GUI also needs design-time-only data
    12	(sample/preview values for bound fields) that must not pollute the canonical template the renderer
    13	consumes. Allowing both editors to write the same file makes the file's content depend on which tool
    14	touched it last, which is the drift the source-of-truth principle (see the editor design) exists to
    15	prevent.
    16	
    17	## Decision
    18	
    19	Make edit ownership a property of each template; never allow two editors to write the same file.
    20	
    21	- A template is either **manual** (file-authored; the GUI may render, print, and preview it but not
    22	  edit it) or **gui** (GUI-owned; the GUI is its only editor).
    23	- Ownership is determined by location: manual templates live in `templates/`, GUI-owned templates in a
    24	  separate writable store (`templates-gui/`). Both classes are YAML files in the same schema and feed
    25	  one registry. For v1 the substrate is folders, not a database; app state (printers, settings, jobs)
    26	  is the thing that warrants SQLite, not templates.
    27	- A one-way **"Convert to GUI edit"** action *moves* a manual template into the GUI store and marks it
    28	  GUI-owned. It is a move, not a copy, so there is never a duplicate id or two diverging sources. The
    29	  reverse direction is a plain "export YAML" download; re-adopting it as manual is a manual file drop,
    30	  not an automatic round-trip.
    31	- Design-time-only data lives in an optional top-level `editor` block in the YAML, owned by the GUI and
    32	  ignored by the renderer. Because the renderer's parser uses `deny_unknown_fields`, this block must be
    33	  added to the schema explicitly. It only ever appears on GUI-owned templates.
    34	
    35	## Consequences
    36	
    37	- The lossy-round-trip problem disappears by construction: the GUI never rewrites a manually-owned
    38	  file, so comments and formatting in `templates/` are safe.
    39	- Both classes render and print identically; ownership gates editing only. The UI shows manual
    40	  templates with a lock badge and the "Convert to GUI edit" action.
    41	- The registry must scan both stores and still reject duplicate ids across them; the move semantics
    42	  keep this from happening in normal use.
    43	- Adding the `editor` block touches the schema (`raw.rs`, `models.rs`, the `TryFrom`) per ADR-0002,
    44	  and the renderer must skip it.
    45	- Converting is intentionally one-way and slightly inconvenient in reverse; this is the cost of keeping
    46	  a single source of edits.

## Findings

### Critical (blocking)

**The replacement top-level field table drops legacy `options:`**
Evidence: `openspec/changes/issue-164-template-groups/specs/template-groups/spec.md:32-49` says the table is the post-change set of top-level template fields and that parsing still rejects unknown fields. That table omits `options`. The project rules explicitly say legacy top-level `options:` still parses and must not be treated invalid (`AGENTS.md:185-187`), and the current parser/converter still accepts and desugars it (`src/raw.rs:112-115`, `src/convert.rs:284-294`). Because this is a first-touch ADDED requirement superseding the frozen `docs/SPEC.md` §3 table (`docs/SPEC.md:292-304`), it must carry the complete post-change contract, including still-accepted legacy fields.
Fix: add `options` to the post-change top-level field table as legacy/deprecated compatibility input that desugars into enum `params`, or explicitly state outside the table that it remains an accepted top-level field despite not being recommended for new templates.

### Moderate

**The new move endpoint does not name the frozen API sections it supersedes**
Evidence: the spec adds `PUT /api/templates/{id}/group` and its response contract at `openspec/changes/issue-164-template-groups/specs/template-groups/spec.md:158-192`, but unlike the list/detail requirements (`spec.md:98-100`, `spec.md:128-129`) it does not say it supersedes the frozen `docs/SPEC.md` §2 endpoint table or §2.0 template management. The frozen API table enumerates template routes and has no group endpoint (`docs/SPEC.md:40-50`), while §2.0 describes the template-management write surface without it (`docs/SPEC.md:85-132`). AGENTS requires first-touch ADDED requirements to name the frozen section they supersede.
Fix: add a supersession sentence to the move-endpoint requirement naming `docs/SPEC.md` §2 endpoint table and §2.0 template management for the addition of this endpoint and its mutation semantics.

**Spec and design disagree on whether quoted existing group values are patchable**
Evidence: the spec says a file is unpatchable when its top-level `group` value “is not a plain scalar” (`spec.md:172-175`). The design says the patcher accepts “plain or quoted scalar” values (`design.md:113-115`). The same spec also declares a quoted group value valid and stripped (`spec.md:64-67`). This leaves implementers unable to know whether `group: "Shipping"` can be moved/cleared or must return `422`.
Fix: change the spec wording from “plain scalar” to “scalar value the patcher can replace unambiguously, including plain and quoted scalars” if quoted scalars are intended, or change the design/scenarios to state quoted existing group lines are refused by the move endpoint.

**The textual key detector can miss YAML-valid top-level `group` keys and insert a duplicate**
Evidence: the design defines detection as a column-0, non-comment line whose key is exactly `group` (`design.md:107-120`). The actual template parser is a YAML parser (`src/parse.rs:25-33`) over a `deny_unknown_fields` struct (`src/raw.rs:102-119`), so valid YAML spellings that deserialize to the same key, such as a quoted key (`"group": Shipping`) or other YAML-valid mapping syntax, are schema-level `group` fields but do not match the proposed textual detector. If the scanner fails to see the existing parsed group, step 6 can insert a second `group:` line (`design.md:118-120`), violating the spec’s “replaces the value of the existing top-level `group:` line” guarantee (`spec.md:163-166`) and creating confusing duplicate-key source even if the readback assertion passes.
Fix: require the patcher to refuse with `422` when the parsed template already has a group but the textual patcher cannot identify exactly one replaceable top-level group line, and add scenarios/tests for quoted-key or otherwise unmatchable existing `group` keys.

**Group filtering behavior for Favorites and Recents is underspecified**
Evidence: the requirement says selecting a group narrows “the grid” and composes with text search (`spec.md:246-249`), and the design says the filter row is above the grid and uses `useMemo` (`design.md:151-153`). The current Labels page also renders separate Favorites and Recent sections when not searching (`ui/src/pages/Templates.tsx:145-150`, `ui/src/pages/Templates.tsx:207-226`), independent of the main filtered grid (`ui/src/pages/Templates.tsx:229-232`). Without an explicit rule, an implementation can select `Warehouse` while still showing favorite/recent cards from other groups above the filtered grid, undermining the purpose of group browsing.
Fix: specify whether an active group filter hides Favorites/Recents or filters those sections by the same group, and add an empty-state expectation for the selected group plus search case.

### Suggestions

**Clarify deferred follow-up issue handling**
Evidence: proposal says out-of-scope items are “filed separately if wanted” (`proposal.md:60-61`), while design calls renaming and drag-and-drop “follow-on issues” without issue links (`design.md:35-36`). AGENTS says work not done now becomes an issue, not a parked TODO (`AGENTS.md:30-34`).
Fix: either remove the “filed separately/follow-on issues” language or replace it with actual linked issue numbers if those are committed follow-ups.

Fix: require the patcher to refuse with `422` when the parsed template already has a group but the textual patcher cannot identify exactly one replaceable top-level group line, and add scenarios/tests for quoted-key or otherwise unmatchable existing `group` keys.

**Group filtering behavior for Favorites and Recents is underspecified**
Evidence: the requirement says selecting a group narrows “the grid” and composes with text search (`spec.md:246-249`), and the design says the filter row is above the grid and uses `useMemo` (`design.md:151-153`). The current Labels page also renders separate Favorites and Recent sections when not searching (`ui/src/pages/Templates.tsx:145-150`, `ui/src/pages/Templates.tsx:207-226`), independent of the main filtered grid (`ui/src/pages/Templates.tsx:229-232`). Without an explicit rule, an implementation can select `Warehouse` while still showing favorite/recent cards from other groups above the filtered grid, undermining the purpose of group browsing.
Fix: specify whether an active group filter hides Favorites/Recents or filters those sections by the same group, and add an empty-state expectation for the selected group plus search case.

### Suggestions

**Clarify deferred follow-up issue handling**
Evidence: proposal says out-of-scope items are “filed separately if wanted” (`proposal.md:60-61`), while design calls renaming and drag-and-drop “follow-on issues” without issue links (`design.md:35-36`). AGENTS says work not done now becomes an issue, not a parked TODO (`AGENTS.md:30-34`).
Fix: either remove the “filed separately/follow-on issues” language or replace it with actual linked issue numbers if those are committed follow-ups.
