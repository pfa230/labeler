## Why

Implements [#337](https://github.com/pfa230/labeler/issues/337). `LabelInput` is `{ data }` with no `deny_unknown_fields` (`src/models.rs:1255-1257`, derive `1254`), so any other key on a label (`option`, a misspelling of `data`) is dropped without a word. A caller gets a rendered label built from nothing and no indication why. Silence here is what the no-silent-fallback rule forbids: when the service cannot do what was asked, it says so rather than approximating. The wire already cannot carry `option` to `normalize_option`'s raising branch — every production call site passes `None` (`src/api.rs:2677,2681`, `src/batch.rs:105-106`) and `LabelInput` has no `option` field — but without `deny_unknown_fields` the key is silently dropped rather than reported; closing the envelope retires `options_not_supported` and, with the envelope now strict, the slug's raising branch is deleted here (#214 deletes remaining plumbing).

## What Changes

**BREAKING.** Pre-1.0: no migration, no deprecation window, no alias.

- Make `RenderLabelRequest` an explicit `#[serde(deny_unknown_fields)]` struct `{ template: String, data: HashMap<String, Value> }` (replacing `#[serde(flatten)] pub label: LabelInput` at `src/models.rs:1220`, struct `1221`, fields `1222-1224`) and add `#[serde(deny_unknown_fields)]` to `LabelInput` (`src/models.rs:1254`). In serde 1.0.229 the flattened outer collects unmatched fields while `FlatStructAccess` gives the flattened inner only matching keys; even denying both leaves `{"template","dataa"}` reporting `missing field `data`` rather than `unknown field `dataa`` and `option` without the `, expected `data`` clause (review-2/3 verified against pinned serde 1.0.229 / serde_json 1.0.151), and utoipa 5.5.0 emits `RenderLabelRequest` as `allOf: [{ $ref: LabelInput }, { template }]` with `LabelInput`'s `additionalProperties: false` inside one branch, so the valid body `{"template":"shelf","data":{…}}` fails its own schema. An explicit struct keeps the wire shape (`{ "template": "...", "data": {…} }`) but each type reports its own `expected` clause while status, `code`, `reason` and the named key hold uniformly (``unknown field `option`, expected `template` or `data``` on `RenderLabelRequest`, ``unknown field `option`, expected `data``` on `Vec<LabelInput>` paths, ``unknown field `dataa`, expected `template` or `data``` / ``unknown field `dataa`, expected `data```) and yields a single-object OpenAPI schema `{ template, data, additionalProperties: false }`. `BatchRequest.labels` and `TemplateInputsRequest.labels` remain `Vec<LabelInput>` (no flatten) and are covered by `LabelInput`'s denial alone.
- The rejection arrives through the `Json` extractor (`src/extract.rs`), which maps a deserialization failure to `400 InvalidRequest` with `details.reason` `json_malformed` carrying the parser's backticked message in `details.error` (`src/errors.rs:483-501`, `request-error-envelope`, cf. `src/lib.rs:3613-3614,3669-3670`). Because `Json<RenderLabelRequest>` is an extractor at `src/api.rs:2591`, axum completes deserialization **before** calling the handler at `src/api.rs:2667` (`FormatUnknown`), so an unknown *envelope* key and a bad `format`/`color_mode`/`resolution` query together report `json_malformed`, not `format_unknown`. This envelope ordering does **not** change `request-data-keys:70-76` — `FormatUnknown` at `src/api.rs:2667` still precedes `validate_label_data_keys` at `src/api.rs:2673` for an unrecognized key *inside* `data`, and no delta for that capability is needed.
- Remove the `option` key from the UI: `ui/src/lib/livePreview.ts:44,46` which still adds `{ option: input.option }` when its input carries one, and `ui/src/api/types.ts:101-102` where `TemplateInputsRequest.labels[].option` explicitly permits the same key on `POST /api/templates/{id}/inputs`. No caller populates `PreviewInput.option` today, but both must be gone before this lands or the row preview and any typed `inputs` client start failing the moment one does. The `option` sort branch in `previewKey` goes with it.
- Retire and delete `Reason::OptionsNotSupported` (`options_not_supported`, `src/reason.rs:69`) and the `OptionsNotSupported` branch in `normalize_option` (`src/render/mod.rs:1224-1229`) **in this change**. That branch is already unreachable at HEAD (every production call site passes `None`), and after the explicit `RenderLabelRequest` + `LabelInput` denials no future label can carry `option` as an envelope key; CSV `option.<name>` columns remain live under `csv_option_column_unknown` (`docs/SPEC.md:758`) and are not this slug. Deleting the variant here satisfies the mandatory post-archive gate `spec_documents_every_reason_and_invents_none` (`src/errors.rs:665`, `scan_canonical_withdrawals` `src/errors.rs:732-765`), which fails when a canonically withdrawn slug remains in `Reason::ALL` and `AGENTS.md` requires `archive` before `cargo test`; deferring to #214 would fail it. #214 retains remaining plumbing deletions (`Options` struct, `TemplateContent::options()`, rest of `normalize_option`, UI grid `option` maps at `ui/src/lib/labelGrid.ts:17`/`connectorRows.ts:101`) with `skip_specs: true`. Expect a pre-archive phantom failure `SPEC §10.1 documents reasons that do not exist: ["options_not_supported"]` — `scan_canonical_withdrawals` scans only `openspec/specs` (not deltas) while the additive half scans deltas (`src/errors.rs:771-773`); this is specified at `openspec/specs/layout-sizing/spec.md:1088-1096` (pre-archive withdrawn slugs remain expected; archive removes it).

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

 - `template-inputs`: requirement "The service computes an input list for a given label" superseding its `A key other than data on a label SHALL be ignored … Retiring the vestigial option map from the UI is #214` paragraph (`spec.md:284-287`). The replacement makes `RenderLabelRequest` an explicit strict struct and `LabelInput` strict, so a label SHALL carry exactly `data` and any other envelope key (including `option` or a misspelling) SHALL be refused as `json_malformed` on all three endpoints; status, `code`, `details.reason` and the backticked `unknown field` name hold uniformly, `expected` lists the fields of the type that failed (``expected `template` or `data``` vs ``expected `data```), and OpenAPI `additionalProperties: false` is correct. The `POST /api/templates/{id}/inputs` lenient-resolution boundary (keys *inside* `data` naming no declared parameter are still ignored) is unchanged beyond that envelope replacement, and the envelope's `json_malformed` vs. `FormatUnknown` ordering for the `Json` extractor is documented. This delta also carries a first-touch `ADDED` requirement withdrawing the `options_not_supported` row that `docs/SPEC.md` §10.1 publishes under `InvalidRequest` — complete post-change contract: slug withdrawn, no code path raises it (variant deleted here; `option.<name>` CSV columns remain live under `csv_option_column_unknown`).

## Impact

- **Code.** `RenderLabelRequest` becomes explicit `{ template, data }` with `#[serde(deny_unknown_fields)]` replacing the `flatten` (`src/models.rs:1220-1225`), `LabelInput` gets `#[serde(deny_unknown_fields)]` (`src/models.rs:1254`); deletion of `Reason::OptionsNotSupported` (`src/reason.rs:69`) and its `normalize_option` branch (`src/render/mod.rs:1224-1229`); render/label handler moves from `req.label.data` to `req.data`; `ui/src/lib/livePreview.ts` (delete `PreviewInput.option`, `hasOpt` guard and both `option` spreads + `previewKey` branch, lines 8,19,44,46) and `ui/src/api/types.ts:101-102` (`option` removed from `TemplateInputsRequest`). OpenAPI at `src/openapi.rs:141,146` now emits a single object for `RenderLabelRequest` (no `allOf`).
- **API.** A label carrying `option`, a misspelled key, or any other key besides `data` now fails with `400 InvalidRequest / json_malformed` with backticked ``unknown field `option`, expected `template` or `data``` / ``unknown field `option`, expected `data``` and ``unknown field `dataa`, expected `template` or `data``` / ``unknown field `dataa`, expected `data``` in `details.error`, instead of rendering. A well-formed label is unaffected. No new status or `code`; the existing `request-error-envelope` mapping applies, with envelope `json_malformed` vs. `FormatUnknown` precedence noted but `request-data-keys:70-76` (data key inside `data`) unchanged.
- **Tests.** New HTTP tests pin the rejection for `option` and for a misspelled key on all three endpoints, naming status and `code`/`reason`, and verify backticked `unknown field` `details.error` (`expected `template` or `data`` vs `expected `data`` per type); existing invalid fixtures at `src/lib.rs:2022`, `2194`, `2228` that send `{"option":{…},"data":{…}}` and expect `200` will be updated to `{"data":{…}}` so `cargo test` stays green (plus `cargo fmt`/`clippy`). Pre-archive, `cargo test` is expected red with phantom `["options_not_supported"]` until `openspec archive` (layout-sizing:1088-1096); post-archive green. `src/lib.rs:7740` (2.1 MiB `DefaultBodyLimit`) stays green.
- **Docs.** `docs/SPEC.md` is frozen and is not edited. `openspec/specs/template-inputs/spec.md` carries the complete post-change contract; `request-data-keys` carries no delta for this change.
