### Blocking

**1. Task 6.4 is unperformed and nothing downstream will catch it.** `openspec/specs/datetime-params/spec.md:4-7` still declares the capability's Purpose as covering "how that instant defaults to the render instant of the request". That fallback is exactly what this change removes. The delta at `openspec/changes/issue-241-no-inferred-defaults/specs/datetime-params/spec.md` opens directly at `## ADDED Requirements` with no `## Purpose` block, so `/opsx:archive` syncs requirements and leaves the stale sentence in place, and `archive-merge-check.sh` only compares requirements. The published capability would land contradicting its own first requirement. The box is honestly left `[ ]`; it still has to be done before this can be archived.

**2. `docs/AUTHORING.md:576` misstates what the migration this change prescribes actually does.** It reads: `default: "{sys.now}"` "to default to the current render instant". A bare `{sys.now}` renders `%Y-%m-%d` (`src/datetime_fmt.rs:183`, and `docs/AUTHORING.md:572` says so two lines above), and `resolve_and_coerce_default` then feeds that date string to `parse_datetime_override`, which resolves a date-only value to local midnight (`src/datetime_fmt.rs:45-50`). So a `time: true` parameter defaulted that way prints `00:00`, not the wall clock. The proposal calls this out explicitly ("local midnight, because `{sys.now}` renders `%Y-%m-%d`") and the `datetime-params` delta says "the render **date**", but the one document an author actually reads says "instant". The example block at `docs/AUTHORING.md:558-568` compounds it by putting `default: "{sys.now}"` on `printed_on` immediately above a `time: true` sibling. This is a new trap introduced by this change, in the file task 6.3 was scoped to make honest.

### Non-blocking, should be addressed

**3. Two tasks are checked `[x]` but only partly performed.**
- 5.17 asks for a UI test that "a grid selection reaches `data`". There is none: `ui/src/components/LabelGrid.test.tsx` is untouched, and the sibling-`option` write path survives at `ui/src/components/LabelGrid.tsx:77-95` and `:190-197`. What task 4.6 actually edited was `resolveLabels` (`ui/src/lib/labelGrid.ts:38-49`), which has no production caller at HEAD or now (`git grep resolveLabels HEAD -- ui/src` hits only the file and its own test). `optionNames`/`optionValues` are never passed to `LabelGrid` by either page, so nothing user-visible is broken, but the spec scenario "A grid selection reaches the request" is proven by neither code nor test. 5.17's live-preview clauses (undefaulted `datetime` renders, undefaulted `enum` renders, preview and thumbnail agree on `{printed_on:time}`) are also uncovered; only the `sampleData` unit assertions in `ui/src/lib/preview.test.ts:6-27` landed.
- 5.13 asks for the attribution boundary as a pair. `src/datetime_fmt.rs:313-329` covers the parser, and `param_default_unresolvable_http_tests` case 3 covers a default failing as 422, but no test carries the *same* DST-skipped value down both paths to show 400/`datetime_param_invalid` against 422/`param_default_unresolvable`.

Per AGENTS.md, "a checked box is a claim the next reader trusts instead of redoing the work" — these should be unchecked or completed.

**4. The coercion rule is duplicated, not shared.** `resolve_and_coerce_default` (`src/render/mod.rs:367-521`) reimplements the boolean, integer, length/number and enum coercion arms verbatim from the supplied-value path (`src/render/mod.rs:169-278`). The `param-resolution` delta requires a default to be "validated and coerced by **exactly** the rule a value the caller supplied for that parameter is validated and coerced by", and the repo's own precedent is the opposite pattern: `resolver.rs` shares `resolve`/`available`/`requirement` between load and render precisely "so the two cannot drift the way they did in #150 and #155" (AGENTS.md). I checked the two copies and they agree today, so this is not a live bug, but "exactly the same rule" is currently a promise held by copy-paste. Extracting one coerce function taking an error constructor would satisfy the requirement structurally.

**5. `resolve_parameters`/`resolve_parameters_mode` still take a `now` they never read.** `src/render/mod.rs:66` is `_now: DateTime<Local>`, and every one of the twenty call sites computes and passes it alongside the `DateTimeResolver` that already carries the same instant. Clippy stays quiet because of the underscore. Dead parameter, introduced by this change; drop it.

**6. A caller bug is reported as a template bug.** `src/render/mod.rs:356-357`: in strict mode, when `variables` or `datetime` is `None` and the default carries a token, the response is `422 TemplateInvalid` / `param_default_unresolvable` naming the parameter. Nothing is wrong with the template; the caller forgot to thread the environment. AGENTS.md forbids exactly this shape ("never substitute an approximation and carry on"). Production always passes both, so it is unreachable today, but the two `Option`s make it easy to reach later and the error sends the operator to edit a correct template. Either make the pair non-optional on the strict path or raise an internal error there.
