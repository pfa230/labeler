### Critical

1. The batch contract forbids rasterizing any label when the request ultimately fails, but the design explicitly preserves a loop that renders earlier valid labels before discovering later failures. The spec says a failed request “SHALL NOT have rasterized” an artifact ([batch-validation/spec.md:23](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/batch-validation/spec.md:23)), while the design rejects preflight and places the check inside the existing loop ([design.md:63](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/design.md:63)). That loop immediately renders each PNG and retains its bytes, only returning `BatchInvalid` after all labels have been visited ([batch.rs:91](/home/pfa/projects/labeler/.worktrees/issue-324/src/batch.rs:91), [batch.rs:118](/home/pfa/projects/labeler/.worktrees/issue-324/src/batch.rs:118)); PNG rendering performs rasterization at [render/mod.rs:858](/home/pfa/projects/labeler/.worktrees/issue-324/src/render/mod.rs:858). Thus a valid label 0 is rasterized before an unknown key on label 1 is found. This is also an unobservable internal guarantee beyond the issue’s atomic-output requirement. The contract and design must choose consistently between a true preflight phase and preserving the existing per-label rendering loop.

2. The proposed shared validator cannot produce both error contracts its design assigns to it. The design fixes its signature as `(&TemplateDefinition, &HashMap<...>) -> AppError` and says it serves four call sites ([design.md:34](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/design.md:34)), but the specs require ordinary requests to emit `data_key_unknown` ([request-data-keys/spec.md:44](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/request-data-keys/spec.md:44)) and CSV imports to emit a differently worded, differently slugged `csv_data_column_unknown` ([request-data-keys/spec.md:125](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/request-data-keys/spec.md:125)). Neither argument tells the function which contract applies. The plan must define whether shared code merely returns sorted unknown names, accepts explicit error context, or uses separate validators.

### Moderate

3. The CSV integration point does not satisfy the specified phase ordering. The contract requires `csv_data_column_unknown` before any row is built ([request-data-keys/spec.md:127](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/request-data-keys/spec.md:127)), while also preserving `csv_row_invalid` and `csv_empty` ahead of it ([request-data-keys/spec.md:154](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/request-data-keys/spec.md:154)). The design places it after the existing option-column check ([design.md:75](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/design.md:75)), but that check currently runs only after `parse_csv_rows`, which has already constructed every `ParsedCsvRow` ([api.rs:2254](/home/pfa/projects/labeler/.worktrees/issue-324/src/api.rs:2254), [api.rs:2714](/home/pfa/projects/labeler/.worktrees/issue-324/src/api.rs:2714)). The design needs an explicit parsing/validation phase split that reconciles these precedence requirements.

4. `/api/print` failure cardinality is left ambiguous when `copies > 1`. The replacement batch contract promises exactly one failure per failing “label” ([batch-validation/spec.md:28](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/batch-validation/spec.md:28)), but its `copies: 3` scenario does not say whether the response contains one failure or three ([batch-validation/spec.md:92](/home/pfa/projects/labeler/.worktrees/issue-324/openspec/changes/issue-324-a-render-request-may-carry-a-key-no-para/specs/batch-validation/spec.md:92)). The current handler expands the one submitted map into three indexed `LabelInput`s ([api.rs:2555](/home/pfa/projects/labeler/.worktrees/issue-324/src/api.rs:2555)), and the batch loop would produce three entries ([batch.rs:93](/home/pfa/projects/labeler/.worktrees/issue-324/src/batch.rs:93)). Because this is observable API behavior in a complete replacement contract, the intended indices and count must be stated.
