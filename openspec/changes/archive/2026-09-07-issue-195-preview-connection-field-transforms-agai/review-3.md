1. **The delta weakens issue #195’s accepted response contract.** The issue requires source, derived fields, and match status “for each row” (`.agent-runs/issue-195.md:51-56`). The proposed contract instead permits the service to omit all remaining row entries after exhausting its budget (`specs/connector-field-transforms/spec.md:279-282`) and quietly narrows the UI obligation to “each reported row” (`specs/connector-field-transforms/spec.md:358-365`). That is a substantive scope change, contrary to `openspec/config.yaml:51-52`, not merely an implementation bound. The plan needs a response design that preserves the accepted per-row contract, or an explicit change to the issue’s accepted scope.

2. **The response budget still does not establish the bound claimed for it.** The proposal says 65,536 bytes caps row detail (`proposal.md:39-43`), and the design concludes the worst case is roughly 100 KiB (`design.md:76-79`). But each rule repeats every row’s `id` (`specs/connector-field-transforms/spec.md:168-178`), while truncation is defined only for `source_value` and `derived` values and “reported values” is never defined to include IDs, keys, or serialized JSON bytes (`specs/connector-field-transforms/spec.md:274-282`). Homebox accepts an upstream ID as an arbitrary string (`src/connector/homebox.rs:451-454`) and copies it into every row reference (`src/connector/homebox.rs:548-552`); one large ID can therefore be repeated across as many as 32 rule reports. If IDs count toward the budget, the delta must say so and define the byte accounting; if they do not, the claimed row-detail and approximate response bounds are false.

3. **The stale-response fix fails for concurrent requests over the same candidate list.** The design itself notes that two presses can resolve out of order (`design.md:260-263`) but keys results only by serialized candidate rules (`design.md:265-269`) and rejects request sequencing as an alternative (`design.md:271-272`). Two previews of the same rule without an intervening edit have identical keys, so an older live fetch can arrive last and overwrite the newer result. The normative contract only rejects responses after the candidate list changes (`specs/connector-field-transforms/spec.md:371-376`) and therefore does not close this case.

4. **The schema deltas do not follow the repository’s precedence and first-touch rules.** The current normative requirement defines the complete `FieldSpec` shape as `{ key, label, ty, tier, multi_valued }` (`openspec/specs/connector-multi-valued-fields/spec.md:76-85`), yet `transform_source` is introduced only as an ADDED requirement in another capability (`specs/connector-field-transforms/spec.md:3-18`), despite `openspec/config.yaml:73` requiring later changes to an existing requirement to use MODIFIED. Separately, `ResourceSpec` remains documented only by frozen `docs/SPEC.md:871-874`; the delta adds `dynamic_source_prefix` and `fields_incomplete` without providing the complete post-change `ResourceSpec` contract, and the incompleteness requirement does not name the frozen section it supersedes (`specs/connector-field-transforms/spec.md:63-78`). That violates the first-touch rule at `openspec/config.yaml:65-68` and would leave the archived contract fragmented and contradictory.

VERDICT: REVISE
