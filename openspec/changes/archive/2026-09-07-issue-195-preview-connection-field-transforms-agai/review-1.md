1. **The source-picker contract is incompatible with actual validation.** The delta excludes every `tier: derived` field and claims this is “exactly” what save-time validation accepts (`specs/connector-field-transforms/spec.md:143-146`; `design.md:117-123`). However, Homebox statically declares `location_url` as single-valued text with `Tier::Derived` (`src/connector/homebox.rs:116-121`), and validation accepts any static single-valued text column without checking its tier (`src/connector/mod.rs:196-205`). Conversely, validation accepts any `custom:` source without proving the schema reports it (`openspec/specs/connector-field-transforms/spec.md:90-96`). The current schema therefore cannot identify the exact accepted set: `tier` does not distinguish connector-derived fields from transform-derived fields, and dynamic-prefix values may be accepted without appearing in the schema. The plan needs a new source-eligibility representation or an explicit decision that the UI offers only a subset of valid sources.

2. **The planned “schema unavailable” behavior cannot detect the upstream failure it is intended to handle.** The design says the schema needs the upstream and that an unreachable upstream makes the editor read-only (`design.md:125-138`; `specs/connector-field-transforms/spec.md:155-159`). Homebox instead converts every failure from its custom-field schema request into an empty list with `unwrap_or_default()` and returns a successful schema (`src/connector/homebox.rs:243-267`). An unreachable or unauthorized upstream therefore appears to the UI as a successfully loaded but incomplete schema. The plan must decide whether schema discovery failures make the endpoint fail or whether the response exposes partial/incomplete schema state; the proposed UI behavior cannot be implemented from the current response.

3. **The rule-major response creates substantial unchecked response amplification.** Every applied rule repeats every row’s source value and captures (`design.md:41-54`; `specs/connector-field-transforms/spec.md:37-46`), while preview inherits browse’s limit of 200 rows (`specs/connector-field-transforms/spec.md:28-30`; `src/connector/homebox.rs:321`) and accepts up to 32 rules with source values of 8,192 bytes still eligible for evaluation (`openspec/specs/connector-field-transforms/spec.md:319-328`). Thirty-two valid rules reading the same 8,192-byte field across 200 rows produce about 52 MiB of repeated source text alone, before captures and JSON overhead; longer non-matching values can amplify the upstream body further because the response still reports them. The plan supplies no preview-response budget, truncation contract, or deduplicated topology.

4. **Preview results are not tied to the candidate snapshot that produced them.** The request contains every candidate rule because ordering and collisions matter, but the UI contract only says to display the returned panel (`specs/connector-field-transforms/spec.md:161-171`). It does not invalidate results when any rule is edited, reordered, added, or removed, nor prevent an older in-flight response from overwriting a newer result. A conforming implementation could therefore show results from candidate list A beside candidate list B—the exact misleading feedback this change is meant to eliminate.

VERDICT: REVISE
