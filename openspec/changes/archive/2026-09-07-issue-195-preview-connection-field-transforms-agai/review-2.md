1. **The editor can preview against different connection details from those being saved.** Preview always uses the stored base URL and credential (`specs/connector-field-transforms/spec.md:83-86`), while the same edit form permits changing both (`specs/connections/spec.md:21-34`). Results are invalidated only when transform rules change (`specs/connector-field-transforms/spec.md:291-296`), and the design keys them solely by serialized rules (`design.md:207-214`). An operator can therefore change the base URL or API key, preview against the old upstream, and save those rules alongside the new connection details while the misleading result remains visible. The plan needs a contract and design for this state—such as making transforms read-only, omitting them from save, and disabling/discarding preview until connection-access changes are saved.

2. **The normative delta does not define the new JSON wire format.** The issue explicitly delegates exact response field names to the planner (`.agent-runs/issue-195.md:51-56`), but the delta describes response members only semantically (`specs/connector-field-transforms/spec.md:110-125`) and never names the per-row or top-level truncation flags (`specs/connector-field-transforms/spec.md:214-221`). Likewise, the two schema additions are described as “marks” without property names, types, or required/optional status (`specs/connector-field-transforms/spec.md:3-28,49-63`). The design’s sketch supplies some preview names but omits both truncation fields and both schema-field names (`design.md:45-59`). Because only synced specs become normative (`openspec/config.yaml:73-76`), implementations could choose incompatible OpenAPI shapes while satisfying the published prose.

3. **The source picker does not meet the accepted “exactly what save accepts” scope.** Save accepts any source under a connector’s dynamic text prefix even when discovery did not report it (`openspec/specs/connector-field-transforms/spec.md:90-96`), but the proposed delta expressly leaves such sources unmarked and calls the picker a subset (`specs/connector-field-transforms/spec.md:19-23`). The editor then offers only marked columns (`specs/connector-field-transforms/spec.md:253-260`). Consequently, a new valid `custom:` transform becomes unauthorable whenever discovery is incomplete, despite the existing guarantee that an unreachable upstream does not prevent saving transforms (`openspec/specs/connector-field-transforms/spec.md:103-104`). Merely warning that the list is incomplete does not satisfy the issue’s exact-set requirement (`.agent-runs/issue-195.md:64-69`); the plan needs a product-level resolution for dynamic-prefix sources.

4. **The `page_size` contract both changes accepted scope and lacks enforcement.** The issue says preview bounds follow browse’s bounds (`.agent-runs/issue-195.md:46-47`), and browse clamps to `1..=200` (`src/connector/homebox.rs:321`), whereas the plan deliberately introduces a different maximum of 50 (`specs/connector-field-transforms/spec.md:211-213`; `design.md:116-121`). Separately, the design only clamps the value sent upstream, but the connector collects every returned item without enforcing that requested limit (`src/connector/homebox.rs:370-374`). It therefore cannot guarantee the delta’s scenario that at most 50 rows are fetched and reported (`specs/connector-field-transforms/spec.md:228-231`) when an upstream over-returns. The contract also omits the behavior of `page_size: 0`, although the design silently chooses clamping to 1.

VERDICT: REVISE
