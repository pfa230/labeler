### Blocking

**1. Task 7.9's first half is checked and no such test exists.** `grep -n "issue_262" src/lib.rs` returns fourteen tests; `issue_262_put_template_returns_param_defaults` (`src/lib.rs:10474`) covers the second half ("a successful write returns a detail body carrying `param_defaults`"), and nothing covers the first: "a store read failing on a write path returns `500` **and** leaves no template file written, moved or replaced". `grep -n "store read\|store failure" src/lib.rs` finds only two unrelated `.expect("store read")` at `:6465` and `:6486`. That ordering is the single invariant this change newly introduces, and the delta pins it with a normative scenario (`specs/template-inputs/spec.md:1145-1149`). Moving `src/api.rs:779-787` below `stage_and_replace` today would pass fmt, clippy, every test and both gate scripts.

It is not hard to write, which is why the box being checked is the problem rather than the gap. `Store::set_setting` is public (`src/store.rs:307`) and the test harness already reaches it (`src/lib.rs:10147` uses `state.store().set_variable`), `DATETIME_FORMATS` is `"datetime_formats"` (`src/settings.rs:11`), and `resolve_datetime_formats_from` returns `SettingError::Corrupt` on unparseable JSON (`src/settings.rs:152-157`), which `src/api.rs:781-783` maps to `AppError::internal` → 500. So: store `"{"` under that key, `PUT /api/templates/<new-id>`, assert `500` and that no file for that id exists under the templates dir. This finding has been raised in rounds 1, 2 and 3 and is still open.

**2. ADR-0068 is not marked as superseded in part by ADR-0093.** `docs/adr/README.md:7-8` states the rule: "add a new ADR that supersedes the old one (mark the old one `Superseded by ADR-NNNN` and the new one `Supersedes ADR-NNNN`)". ADR-0093 declares "Supersedes in part [ADR-0068]" (`docs/adr/0093-…md:7`), but the 0068 row is untouched (`git diff docs/adr/README.md` adds only the 0093 row). The repo records partial supersessions in that row, twice, in the very same line: `docs/adr/README.md:80` reads "Accepted (token list and formatting syntax superseded by [0079]; render-instant default superseded by [0088])". The cacheability supersession this change makes belongs there on the same terms. `tests/adr_index.rs` does not check this, so nothing else will catch it. One line.

### Non-blocking

**3. ADR-0093 Context §2 still inverts the pre-change rule.** "Derivation previously omitted token-bearing defaults from `InputSpec.default`, causing parameters with authored defaults to appear required or unseeded in forms." The old code set `required = spec.default.is_none()` and the proposal quotes it (`src/templates.rs:401` pre-change), so a token-bearing default made the parameter `required: false` — unseeded, yes; "appear required", no. That is exactly the contradiction the issue is about, and the ADR states it backwards. The `ParamSpec` half of this finding (round 3 #9) is fixed.

**4. The slider branch substitutes a value of its own, and a less truthful one than before.** Task 6.4 asked `ParamInput` to stop substituting a default for an absent value in the checkbox, select and slider branches. The checkbox and select branches now do (`ParamInput.tsx:185`, `:207`). The slider replaced `Number(spec.default)` with `Number(spec.min ?? 0)` (`ParamInput.tsx:129`), and `isSlider` requires `hasDefault` (`:121-123`), so this line only ever runs for an entry that *has* a published default — the readout at `:151` would name `min` for a value the render would resolve to the default. After this change `spec.default` is the resolved value, so the line it replaced had become the truthful one. I could not reach it in-tree: `ParamInput` is used only from `FieldForm.tsx:100`, every entry publishing a default is seeded (`PrintForm.tsx:26-31`, `:46-49`), and a `type="range"` never emits `""`. So it is currently dead, and untested in both directions.

**5. The catalog test does not go through `catalog-index.rs`.** `issue_262_catalog_empty_vars_lists_broken_default_as_field` (`src/lib.rs:10565`) rebuilds the binary's context inline — empty map, `resolve_datetime_formats_from(None)`, one instant — and asserts the derivation rule. That does test the substance of `specs/template-inputs/spec.md:625-635`, and it can fail against the old code (`needs_var` would not be listed). But `src/bin/catalog-index.rs` still has no test of its own, so changing the context that file passes at `:68-75` would not fail anything. (It is also a `#[tokio::test]` that awaits nothing.)

**6. Neither half of task 7.6 is asserted for a resolved value.** `issue_262_inputs_every_label_carries_same_default` (`src/lib.rs:10517`) uses `default: hello`, a literal, so the two labels agree whether or not the map is shared — it cannot detect per-label re-resolution. And no test compares `GET /api/templates/{id}` against `POST /…/inputs` for a *resolved* default under one snapshot; `inputs_endpoint_infallible_for_unresolvable_default` (`:9182-9229`) covers only the failure case. The structural guarantee is real and readable in `src/templates.rs:2221-2247` and `src/api.rs:1322-1334`; the test is what does not add to it.

**7. The thumbnail requirement's stated consequence does not hold for a non-interpolated broken default.** `specs/template-inputs/spec.md:449-452` says a parameter whose default fails to resolve is invented for "on exactly the terms it invents for a parameter declaring no default at all", and concludes "The preview therefore renders where a caller's render of the same template would be `422 TemplateInvalid`." The `SHALL` above it gates invention on `interpolated && required` (`:430-433`), which `placeholder_data` implements (`src/templates.rs:181`). So a parameter read only by a `when:` gate, with a broken default, gets no placeholder and the thumbnail still fails strict resolution with `param_default_unresolvable`. The implementation matches the `SHALL`; the prose overreaches. No regression — that case fails today too — and the new test covers the interpolated case only (`src/lib.rs:10238`).

**8. `ParamDefaultFailure` does not make "at most one of `token` and `value`" a type property.** Task 1.1 and `specs/param-resolution/spec.md:159-160` both state it; the struct carries two independent `Option<String>` (`src/render/mod.rs:318-324`) and `new` even has a `(Some, Some)` message arm. No call site constructs both, so the wire shape is correct today; the invariant just rests on the three call sites rather than on the type, unlike `ParamDefaultReport`, which does encode its either/or.
