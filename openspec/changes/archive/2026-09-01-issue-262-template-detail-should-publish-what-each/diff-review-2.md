The round-2 implementer's own log records the decision: *"Remaining `tasks.md` gaps … are test-coverage gaps, not contract violations; the implementation satisfies the spec deltas and gates do not enforce those tests."* That reasoning is wrong on two counts — one of the five is an unimplemented `SHALL`, not a test gap, and the boxes are still checked, which is the violation regardless of whether a gate can see it.

### Blocking

**1. The CSV import grid and the connector grid do not surface `default_error.message`.** `template-inputs`' screen requirement — whose subject is defined at its head as "A screen that collects label data", and which addresses those two grids by name elsewhere in the same requirement — states "the screen SHALL surface the error's `message` against that entry when the list arrives" (`specs/template-inputs/spec.md:660`). `datetime-params` repeats it inside a requirement titled "The print form and the row grids carry a datetime parameter" (`specs/datetime-params/spec.md:28`), with its own scenario at `:79`. `Import.tsx:147-151` and `Connect.tsx:178-182` write only the literal `"required"` into the per-cell message map; `grep -rn default_error ui/src` returns hits only in `types.ts:48`, `FieldForm.tsx:95-97` and `FieldForm.test.tsx`. The print form complies; the grids do not. Both grids already carry a per-cell message channel (`field[input.name] = <message>`), so this is an unwritten line, not a design problem. This is the same finding round 1 raised as #5 and it is untouched.

**2. Task 7.9 is checked and no such test exists.** `grep -n issue_262 src/lib.rs` returns ten tests, all on `GET /api/templates/{id}`, `POST /…/inputs`, the render path, the thumbnail or `GET /api/templates`. None exercises a `PUT` response body for `param_defaults`, and none exercises the store-read-before-mutation ordering. That ordering is the single invariant this change newly introduces, and the delta pins it with two scenarios (`specs/template-inputs/spec.md:1145-1149` and `:1151-1156`). Moving `src/api.rs:779-787` below `stage_and_replace` today would pass fmt, clippy, every test and both gate scripts.

**3. Task 7.12 is checked but two of its five clauses have no test.**
- "`ParamInput` substitutes no default of its own": `ui/src/components/ParamInput.test.tsx` is unmodified, and its three unset-state tests (`:232`, `:244`, `:256`) each pass a spec carrying **no** `default`, so they passed identically before this change. The behavioural change — `value === undefined` *with* `spec.default` present now rendering unset (`ParamInput.tsx:185`, `:207`) — is untested in both directions.
- "`Import` and `Connect` read requiredness from `required` and flag a row whose entry carries `default_error`": neither `Import.test.tsx` nor `Connect.test.tsx` was touched, and neither mentions `default_error`.

**4. Task 7.11 is checked and no test goes through the catalog derivation.** `src/bin/catalog-index.rs` contains no `#[test]` and nothing elsewhere asserts the empty-install field list. The `{vars.…}` half is covered *in substance* one layer down by `src/templates.rs:5756-5759` (`token_def` with an empty variables map is `required`), and the `{sys.…}` half only through the HTTP endpoint (`src/lib.rs:9989`), so the rule is not entirely unguarded — but the delta states it as a catalog scenario (`specs/template-inputs/spec.md:630-635`) and the box claims a test that is not there.

**5. Tasks 7.6 and 7.8 are each still half-done.**
- 7.6's "every label in one inputs body carries the same published default" is not asserted. `issue_262_post_template_inputs_multi_label_batch` (`src/lib.rs:10107`) checks `site_param` on label 1 only; label 2 selects branch `b`, whose text reads `{field_b}` alone, so `site_param` is not an input there and no two labels are ever compared (`src/lib.rs:10186-10193`). The two-endpoint agreement half is covered only for the *failure* case, by `inputs_endpoint_infallible_for_unresolvable_default` (`src/lib.rs:9182-9229`).
- 7.8's "the read-only report carries the same strings with no `param`" is not asserted anywhere. `issue_262_strict_render_fails_with_structured_details_for_broken_default` (`src/lib.rs:10222-10229`) checks the `422` side and the absence of `details.message`; no test compares its `reason`/`message`/`token` against `param_defaults.*.error`, and none asserts that projection omits `param` — which `specs/param-resolution/spec.md:189-196` states normatively and `specs/template-inputs/spec.md:1070-1074` calls byte-identical to `default_error`.

**6. The replacement TemplateDetail assertion is still vacuous.** `ui/src/pages/TemplateDetail.test.tsx:530-532` does `screen.getByText("nodef").closest("div")` and asserts that node's `textContent` does not match `/default:/i`. `getByText("nodef")` returns the `<span className="font-mono font-medium">` at `TemplateDetail.tsx:296`; `closest("div")` therefore returns its parent `<div className="flex items-center gap-2">` (`:294`), which contains only the name span and the type badge. The `default:` block is a **sibling** of that div, inside the `justify-between` row at `:292`. So the assertion passes against an implementation that wrongly rendered a default for `nodef` — the same defect round 1 raised as #7, relocated rather than removed. It is the only coverage for the delta scenario "A parameter with no default shows nothing new" (`specs/template-inputs/spec.md:1191-1194`). Scoping to the card (`closest("div.rounded-md")`, or the `key={name}` card element) would make it able to fail.

### Non-blocking

**7. `resolve_parameter_default` still panics behind a `pub` signature.** `src/render/mod.rs:457` `panic!`s when the spec declares no default. It is unreachable from the one in-tree caller — `resolve_declared_defaults` (`:466`) guards on `spec.default.is_some()` — but the function is `pub` and its signature does not say so, and a panic reached from a request path drops the connection rather than returning an `AppError`. Making the no-default case a type-level impossibility (take the already-unwrapped declared value) would cost nothing.

**8. ADR-0093 Context §1 misstates what changed.** "A template parameter declaring a `default:` was previously published verbatim in `ParamSpec.default` and `InputSpec.default`" reads as though both moved. `ParamSpec` is untouched by design (`design.md`, and `tasks.md` 2.3 says so), and `TemplateDetail.tsx:306` still renders `spec.default` as the *declared* text on purpose. Only `InputSpec.default` changed.

**9. Cosmetic.** `FieldForm.tsx:61` computes `hasDefault` and then `:78` re-spells the same condition inline instead of using it.
