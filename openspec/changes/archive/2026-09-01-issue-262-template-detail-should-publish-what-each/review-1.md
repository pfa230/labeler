1. **MAJOR — The diagnostic wire shape is contradictory.** `template-inputs/spec.md:16` and `:1003-1006` define `error`/`default_error` without `param`, while `param-resolution/spec.md:158-168` requires `param` in the structured payload and says that payload is reused by both fields. `design.md:34-35` and `:58-63` likewise promise structural identity with the render-path `details`. The plan must decide whether read-only diagnostics include `param` or are projections that omit it.

2. **MAJOR — `required` retains two incompatible meanings.** `template-inputs/spec.md:73-79` and `:221-224` make a failed default `required: true`, but `:232-234` says any enum declaring a default remains `required: false`. The datetime contract repeats the conflict: `datetime-params/spec.md:27-29` marks a failed default required, while `:34-38` says requiredness depends exactly on whether a default was declared. These complete MODIFIED requirements cannot be implemented consistently.

3. **MAJOR — Endpoint equality is promised across requests that may legitimately differ.** `template-inputs/spec.md:226-230` and the scenario at `:268-272` require GET detail and POST inputs to return identical defaults without fixing their resolution context. Yet `design.md:138-141` correctly acknowledges that defaults can change between reads across midnight or a variables-store edit. The contract must promise identical resolution rules under equivalent snapshots, not unconditional cross-request value equality.

4. **MAJOR — The design does not establish the required resolve-once data flow.** The contract forbids independent computation (`template-inputs/spec.md:1008-1011`), and `design.md:31-32` claims one resolution projected everywhere. However, the design supplies only a per-parameter wrapper with fresh scratch maps (`design.md:49-53`) and threads raw context independently into `derive_inputs_internal`, `derive_inputs_for_label`, `inputs_all`, `inputs_default`, and `detail` (`:65-68`). No shared request-scoped result is defined despite the one-pass claim at `:143-145`. The design needs an explicit resolved-default result map reused by every projection and, for POST inputs, across its label derivations.

5. **MAJOR — New failure semantics for mutation endpoints are omitted.** `design.md:73-78` requires every TemplateDetail-producing write path to perform the new store reads, while the report contract turns a read failure into `500 Internal` (`template-inputs/spec.md:1017-1020`). The risk analysis claims only GET detail and POST inputs gain this failure (`design.md:124-127`). Existing write paths construct detail only after durable publication or movement (`src/api.rs:827-837`, `:853-867`, `:906-921`, `:1046-1056`), so a straightforward implementation can mutate successfully and then return 500. The plan must specify pre-mutation context capture or explicitly contract and mitigate partial-success responses.

6. **MINOR — The report-keying rationale contradicts the renderer behavior.** `design.md:80-86` says an unreferenced broken default is “still able to fail nothing,” whereas the delta correctly says it can fail a render because all declared parameters are resolved (`template-inputs/spec.md:992-996`). This must be corrected so implementation does not accidentally key resolution to layout usage.
