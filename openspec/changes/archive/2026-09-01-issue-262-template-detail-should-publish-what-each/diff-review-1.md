**Gates I ran myself** [verified]: `cargo fmt --check` clean, `cargo clippy --all-targets --all-features -- -D warnings` exit 0, `cargo test` exit 0, `ui/`: `eslint` exit 0, `tsc --noEmit` exit 0, `vitest` 430/430 pass. `cargo run --bin catalog-index` leaves `catalog/index.json` byte-identical, as `design.md` predicted. `.workflow/specs-digest.sh` returns `51e956d4…`, matching `review.md`'s `SPECS_SHA256`, so `specs/` is untouched since the verdict.

The server-side design is faithfully built: one `ResolvedDefaults` map per request, built once and passed by reference into `param_defaults`, `inputs.default` and `inputs.all` (`src/templates.rs:2221-2247`); the failure payload is one type with two projections (`src/render/mod.rs:317-361`, `src/errors.rs:288-310`); the store reads are hoisted above the first mutating call on both write handlers (`src/api.rs:779-787` sits before `state.before_publish()` at `:838`; `src/api.rs:1004-1012` sits before `resolve_or_create_group(..., true)` at `:1035` and `move_template_file` at `:1064`). `resolve_and_coerce_default` never returns `Err` in `Lenient` mode, so `derive_inputs_for_label`'s `.expect("lenient resolution never fails")` (`src/templates.rs:151`) still holds now that variables and a resolver are threaded in.

The problems are in what `tasks.md` claims was verified.

### Blocking

**1. Task 7.9 is checked and no such test exists.** `grep param_defaults src/lib.rs` returns 17 hits, every one inside a `GET /api/templates/{id}` assertion. Nothing exercises a `PUT`/`POST` response body for `param_defaults`, and nothing exercises the store-read-before-mutation ordering. That ordering is the single invariant this change newly introduces, and the delta pins it with two scenarios ("A store failure refuses a write rather than following it", "Building the report cannot fail after a write lands"). A future edit moving `src/api.rs:779-787` below `stage_and_replace` would pass fmt, clippy, every test and both gate scripts.

**2. Task 7.11 is checked and no such test exists.** `src/bin/catalog-index.rs` contains no `#[test]` and no test elsewhere covers the empty-install derivation. The delta requires a `{vars.…}`-defaulted parameter to be listed as a field and a `{sys.…}`-defaulted one not to be; neither direction is asserted. The CI `catalog-index` step only diffs `index.json`, which is unchanged precisely because no catalog template declares a default — so it proves nothing about this rule.

**3. Task 7.12 is checked but two of its five clauses have no test.**
- "`ParamInput` substitutes no default of its own": `ui/src/components/ParamInput.test.tsx` is unmodified, and its three unset-state tests (`:232`, `:244`, `:256`) all pass a spec with **no** `default`, so they passed identically before this change and cannot detect the removed fallbacks at `ParamInput.tsx:185` and `:207`. The behavioral change — `value === undefined` with `spec.default` present now renders unset — is untested.
- "`Import` and `Connect` read requiredness from `required` and flag a row whose entry carries `default_error`": neither `Import.test.tsx` nor `Connect.test.tsx` was touched, and neither file mentions `default_error`. (Task **6.5** is also checked with no code change; that half is defensible — `Import.tsx:147-151` and `Connect.tsx:178-182` already read `input.required` and never re-derive it — but the checked box records a verification, not an edit, and the test clause is unmet regardless.)

**4. Tasks 7.6 and 7.8 are each half-done.**
- 7.6's "every label in one inputs body carries the same published default" is not asserted. `issue_262_post_template_inputs_multi_label_batch` (`src/lib.rs:10107`) checks `site_param` on label 1 only; label 2 selects branch `b`, where `site_param` is not an input at all, so no two labels are ever compared. The two-endpoint agreement half *is* covered, but only for the failure case, by the updated `inputs_endpoint_infallible_for_unresolvable_default` (`src/lib.rs:9182-9231`).
- 7.8's "the read-only report carries the same strings with no `param`" is not asserted anywhere. `issue_262_strict_render_fails_with_structured_details_for_broken_default` (`src/lib.rs:10200`) checks the `422` side and `details.message` absence; no test compares its `reason`/`message`/`token` against `param_defaults.*.error`, and none asserts that projection omits `param`. That absence is a structural property of `ParamDefaultError` today, but the delta states it as a scenario and the task claims it was tested.

**5. The row grids do not surface `default_error.message`.** `template-inputs`' screen requirement says "the screen SHALL surface the error's `message` against that entry when the list arrives", and `datetime-params` repeats it inside a requirement whose subject is "The print form and the row grids". `Import.tsx:147-151` and `Connect.tsx:178-182` only mark the cell `required`. `FieldForm.tsx:95-99` does surface it, so the print form complies and the grids do not. Task 6.5 asked only for the flag, so this is a plan-to-spec gap rather than a missed task — but it is an unimplemented `SHALL`, and it needs either the implementation or an explicit narrowing of the requirement to the print form.

### Non-blocking

**6. `resolve_parameter_default` panics, and has a wrong-value arm.** `src/render/mod.rs:459` `panic!`s on the internal-error branch, and `:457` returns `Ok(JsonValue::Null)` for a spec declaring no default, which `json_to_param_value` (`:364`, the `other =>` arm) turns into `ParamValue::String("null")`. Both are unreachable from the only caller — `resolve_declared_defaults` (`:464`) guards on `spec.default.is_some()` and passes `Some`/`Some` — but both sit behind a `pub` signature that does not say so, and a panic on a request path drops the connection rather than returning an `AppError`. Returning the internal error as `Err` and making the no-default case a type-level impossibility would cost nothing.

**7. A vacuous assertion.** `ui/src/pages/TemplateDetail.test.tsx:529` — `expect(screen.queryByText(/nodef.*default/i)).not.toBeInTheDocument()`. `TemplateDetail.tsx:294-305` renders the parameter name and the `default:` text in sibling elements, so no single text node can ever contain both "nodef" and "default"; the assertion passes even against an implementation that wrongly rendered a default for `nodef`. It is the only coverage for the delta scenario "A parameter with no default shows nothing new".

**8. ADR wording.** `docs/adr/0093-…md`, Decision §2, says a broken default "publishes `default: null`". It does not — `src/models.rs:129-131` carries `skip_serializing_if = "Option::is_none"`, so the key is absent, which is what the delta requires ("`default` SHALL be absent"). The ADR row in `docs/adr/README.md:102` and the number-against-`main` check are correct, and omitting a back-reference from ADR-0068 matches how ADR-0079 and ADR-0088 already supersede it in part.
